## 1. 本包真正负责什么

`limo_bringup` 是**启动与资源配置包**：把其他包提供的底盘、雷达、建图、定位、导航、可视化节点组合起来，并为它们选择参数、地图和静态 TF。

它没有自己的 C++ 导航算法，也没有注册 Python ROS 节点。其核心入口是各个 launch 文件中的 `generate_launch_description()`：创建 `Node`、`IncludeLaunchDescription` 和参数声明，再返回 `LaunchDescription`。理解“哪些动作真正进入返回列表”，比只看文件名更有用。

| 职责 | 本包中的实现 | 真正执行功能的位置 |
| --- | --- | --- |
| 基础硬件启动 | `limo_start.launch.py` 组合底盘、雷达和安装 TF | 仓库内的 `limo_base`；仓库外的 `ydlidar_ros2_driver` |
| 二维激光建图 | Cartographer launch、Lua、栅格发布入口 | 外部 `cartographer_ros` / Cartographer |
| 已有地图定位与导航 | Nav2 包装入口、地图和导航参数 | 外部 Nav2 的 AMCL、map server、planner、controller、BT 等 |
| RTAB-Map 建图/定位和导航衔接 | RTAB-Map launch、条件分支、导航侧包装入口 | 外部 `rtabmap_sync`、`rtabmap_slam`、Nav2，以及另行启动的相机驱动 |
| 调试和展示 | RViz 配置、键盘入口、I²C 实验脚本 | RViz、键盘控制包或硬件 Python 库 |

本包没有实现巡检任务调度、网页控制、自动充电或多点任务业务。参数中出现 `waypoint_follower`，只表示为外部节点提供配置，不能据此认为已经有完整巡检程序。

## 2. 目录和构建安装关系

```text
limo_bringup/
├── package.xml            # ament_cmake 包声明及部分依赖
├── CMakeLists.txt         # 安装 launch、参数、地图、RViz 等资源
├── setup.py               # 遗留 setuptools 片段，并非本包的构建入口
├── readme.md              # 历史操作记录，部分入口不完整或依赖外部包
├── launch/                # 多种方案的启动文件，含实车模型子入口
├── urdf/                  # 以 base_link 为根、不接管传感器 TF 的显示模型
├── param/                 # 12 个 YAML，含 Nav2、雷达和 ROS 1 风格遗留配置
├── config_files/          # Cartographer Lua 和未被本包入口引用的 slam_toolbox YAML
├── maps/                  # 五组 YAML + PGM 地图
├── rviz/                  # 三份 RViz 配置，含一份 ROS 1 风格配置
└── scripts/               # 历史建图 shell 脚本和 MPU6050 硬件实验
```

### 2.1 构建入口是 CMake

[package.xml](package.xml) 的 `<build_type>` 是 `ament_cmake`，构建工具依赖也是 `ament_cmake`。[CMakeLists.txt](CMakeLists.txt#L18) 只 `find_package(ament_cmake REQUIRED)`，没有 `add_executable()`、Python 安装宏或节点目标。

`install(DIRECTORY ...)` 将下面的目录安装到当前安装前缀的 `share/limo_bringup/`：

```text
rviz/  param/  maps/  config_files/  launch/  urdf/
```

安装语句已经去除原有重复的 `launch` 条目，并包含模型 `urdf/`。`scripts/`、`readme.md` 和本文没有被该规则安装。

多数入口通过 `get_package_share_directory('limo_bringup')` 查找**安装空间**，因此修改源码目录里的地图或 YAML 后，运行时不一定会立即读到新文件。普通构建需重新安装资源；使用符号链接安装时，也应核对实际链接和安装内容。

[setup.py](setup.py) 仅有一个 `setup(data_files=...)` 片段，拟把 launch 文件直接放入 `share/limo_bringup`，也没有 `entry_points`。当前 `ament_cmake` 构建不会自动执行它，不能用这段内容推断本包有可供 `ros2 run limo_bringup ...` 执行的节点。

### 2.2 声明依赖与运行依赖有差距

`package.xml` 声明了常见消息包、TF 和键盘控制依赖，并已补齐建图模型使用的 `launch`、`launch_ros`、`ament_index_python`、`xacro`、`limo_description`、两个 state publisher、`cartographer_ros` 和 `rviz2`。其他入口使用的 `limo_base`、雷达包、Nav2 和 RTAB-Map 等依赖仍未完整声明。

因此：

- 本包作为资源包构建成功，不等于各个 launch 的运行依赖齐全。
- `rosdep` 根据本包清单安装依赖，也不能自动覆盖所有启动方案。
- 仅 `colcon build --packages-up-to limo_bringup`，不能指望把未声明为依赖的 `limo_base` 自动纳入构建。
- `BUILD_TESTING` / lint 部分在 CMake 中整段注释，当前没有启用这些检查。

后续在 Linux/Foxy 环境构建仓库内三个包时，可以使用如下示例；路径需替换为实际克隆位置，本文没有执行这些命令：

```bash
source /opt/ros/foxy/setup.bash
cd /absolute/path/LimoPro/ros2
colcon build --packages-select limo_msgs limo_base limo_bringup
source install/setup.bash
ros2 pkg prefix --share limo_bringup
ros2 pkg executables limo_bringup
```

最后一条用于核对本包没有注册可执行节点。确认包位置时应检查 `ros2 pkg prefix --share`，避免加载到旧的车端工作区。上述构建示例仍不负责补齐外部导航和传感器包。

## 3. 先分清基础层、定位层和导航层

```text
基础层（单独启动，避免重复打开串口）
  limo_start.launch.py
    ├── limo_base/limo_base.launch.py → 底盘节点、/odom、/imu、/limo_status
    ├── ydlidar_ros2_driver/ydlidar_launch.py → 雷达数据
    └── base_link 到 laser_link、camera_link、imu_link 的静态 TF

上层选择一组方案，而不是依次执行所有 launch：
  A. Cartographer 建图 → cartographer.launch.py
  B. 静态地图 + AMCL + Nav2 → limo_nav2.launch.py 或 limo_nav2_ackmann.launch.py
  C. RTAB-Map 建图/定位 → limo_rtab_slam.launch.py
       再按需添加仅导航侧的 limo_rtab_nav2_diff/ackermann.launch.py
  D. 手动拆分定位和导航 → limo_localization.launch.py + limo_navigation.launch.py
       属于有兼容性问题的旧入口，先排查，不能直接当成已验证流程
```

所有上层方案都依赖有效的底盘/传感器输入和 TF。基础层不包含相机驱动；RTAB-Map 的 RGB-D 输入还需要另行提供。若硬件层已经由其他服务启动，不应再次启动同一组底盘和雷达节点。

### 3.1 全部启动入口速查

| 入口，点击查看源码 | 返回列表实际组成 | 前置层与选择关系 |
| --- | --- | --- |
| [limo_start.launch.py](launch/limo_start.launch.py) | 底盘 include、外部雷达 include、三个静态 TF | 基础层；不含建图、定位、Nav2 或相机 |
| [cartographer.launch.py](launch/cartographer.launch.py) | `cartographer_node`、本地 occupancy-grid include、默认启用的模型 include、RViz | 先有基础输入；与 AMCL/RTAB-Map 的全局定位职责互斥 |

| [limo_rtab_nav2_diff.launch.py](launch/limo_rtab_nav2_diff.launch.py) | 外部 `nav2_bringup/navigation_launch.py` + RViz | 先有地图和定位 TF，例如由 RTAB-Map 提供；本入口不启动 RTAB-Map |
| [limo_rtab_nav2_ackermann.launch.py](launch/limo_rtab_nav2_ackermann.launch.py) | 同上，换用 RTAB 阿克曼 YAML | 与 RTAB 差速导航入口二选一；仍需先提供定位层 |

| [limo_navigation.launch.py](launch/limo_navigation.launch.py) | controller、planner、recoveries、BT、waypoint、可选导航 lifecycle manager | 只提供导航侧；仍依赖独立地图和定位来源 |
| [limo_start_navigation.launch.py](launch/limo_start_navigation.launch.py) | 意图合并上述两个本地入口并统一管理生命周期 | **缺少 `return ld`，当前函数返回 `None`**；也不包含硬件基础层 |
| [navigation2.launch.py](launch/navigation2.launch.py) | 外部完整 Nav2 bringup + RViz | 另一个完整导航包装入口；默认参数文件缺失 |
| [limon_teletop_keyboard.launch.py](launch/limon_teletop_keyboard.launch.py) | 一个外部键盘控制节点 | 不提供底盘；不要与导航控制同时争发速度 |

### 3.2 必须避免的组合

- `limo_nav2`、`limo_nav2_ackmann`、`navigation2`、手动拆分的 Nav2 和 RTAB 导航侧包装，属于不同 Nav2 启动方式。一个机器人通常只选择一套，避免重复 controller、planner 和 lifecycle manager。
- Cartographer、AMCL、RTAB-Map 都可能承担 `map → odom` 的发布职责。同一 TF 边应确定一个权威发布者，不能把三套全局定位一起启动。
- 完整 Nav2 bringup 默认已有 AMCL/map server 时，不再叠加本地 `limo_localization`；RTAB-Map 接管定位时，应配合仅导航侧入口并核对实际 `/map` 来源。
- `limo_rtab_slam` 已 include RTAB 子入口，不要再单独启动同一子入口；Cartographer 父入口已包含 occupancy-grid 子入口，也无需重复启动。
- 基础启动和 [另一路雷达启动](../limo_base/launch/open_ydlidar_launch.py) 不能同时抢用同一雷达串口。

## 4. 基础启动：接口与安装 TF 的来源

### 4.1 `generate_launch_description()` 的真实执行路径

[limo_start.launch.py](launch/limo_start.launch.py#L11) 首先查找 `rf2o_laser_odometry`、`ydlidar_ros2_driver`、`limo_base` 的 share 路径，然后才构造并返回启动动作。

实际 include 的是：

```text
limo_base/launch/limo_base.launch.py
ydlidar_ros2_driver/launch/ydlidar_launch.py
```

`rf2o_laser_odometry` 的 include 已注释，但开头的 share 路径查询仍然执行。**即使不使用激光里程计，缺少这个包也会使启动描述生成失败。** 这是解析阶段依赖，不应误判成雷达硬件故障。

`pub_tf = Node(package='limo_base', executable='tf_pub', ...)` 虽被创建，却未加入返回列表，因此当前不启动。仓库内 [limo_base 的 CMake](../limo_base/CMakeLists.txt#L43) 也只构建了 `limo_base`，没有构建 `tf_pub`；不能把这段未使用动作当成有效 TF 来源。

### 4.2 下层底盘默认值与模式

基础入口没有自己声明硬件参数，所含的 [limo_base.launch.py](../limo_base/launch/limo_base.launch.py#L12) 默认值如下：

| 参数 | 默认值 | 当前调用链中的含义 |
| --- | --- | --- |
| `port_name` | `ttyTHS0` | 驱动构造函数补 `/dev/`，连接串口；硬件需匹配 |
| `odom_frame` / `base_frame` | `odom` / `base_link` | 里程计消息和 TF 的父/子 frame |
| `pub_odom_tf` | `True` | 请求底盘广播 `odom → base_link` |
| `use_mcnamu` | `False` | 默认不强制麦轮分支；不是“强制差速”的保证 |
| `odom_topic_name` | `odom` | 下层 launch 传入，但当前驱动直接发布 `/odom`，没有读取这个参数改变话题 |
| `control_rate` | `50` | launch 暴露的参数；不能据此证明串口/反馈按 50 Hz 运行 |

可追踪到 [LimoDriver 构造函数](../limo_base/src/limo_driver.cpp#L36)、[twistCmdCallback()](../limo_base/src/limo_driver.cpp#L428) 和 [模式反馈解析](../limo_base/src/limo_driver.cpp#L263)。实际模式主要来自底盘状态反馈，`use_mcnamu` 才会强制麦轮处理。更换 `nav2_ackermann.yaml` 只更换上层配置，不会替机器人完成机械模式切换。

底盘对外发布 `/odom`、`/imu`、`/limo_status`，订阅 `/cmd_vel`。差速 Nav2 配置 `max_vel_y=0`，即使底盘可横移，这份配置也不会生成横向导航速度。

### 4.3 静态 TF 和实际激光 frame

[三个静态发布动作](launch/limo_start.launch.py#L25) 使用四元数形式的参数，旋转均为 `(0, 0, 0, 1)`：

| 父 frame → 子 frame | 平移 `(x, y, z)`，单位 m |
| --- | --- |
| `base_link → laser_link` | `(0.18, 0, 0)` |
| `base_link → camera_link` | `(0.18, 0, 0.18)` |
| `base_link → imu_link` | `(0, 0, 0)` |

三个动作的节点名却都写成 `base_link_to_base_laser_ydlidar`。frame 边不同，但重名会让节点查询、参数查询和日志定位混乱。以上外参是源码里的固定值，未验证其与实际安装位置一致。

另一个容易混淆的路径是 [param/ydlidar.yaml](param/ydlidar.yaml)：它指定 `/dev/ydlidar`、115200 波特率、`frame_id=laser_frame`、8 Hz、`range_min=0.01`、`range_max=12.0`，并开启 `reversion`、`inverted`、`auto_reconnect`，角度范围为 ±180°。

但 `limo_start` **没有直接加载这份 YAML**；它 include 的是仓库外雷达包自己的 launch。明确加载本地 YAML 的是兄弟包中的 [open_ydlidar_launch.py](../limo_base/launch/open_ydlidar_launch.py#L28)，那条路径另外发布 `base_link → laser_frame`，平移为 `(0, 0, 0.02)`。

所以两个入口的 frame 和外参不同。排查时必须先确认所选入口、运行参数和 `scan.header.frame_id`；不能仅通过修改本地 `ydlidar.yaml` 推断基础入口已经改变。

## 5. TF 链：哪一层负责哪条边

```text
map
 └── odom                       Cartographer / AMCL / RTAB-Map：选定一个全局定位来源
      └── base_link             底盘驱动，pub_odom_tf=true 时广播
           ├── laser_link       limo_start 的静态发布器
           ├── camera_link      limo_start 的静态发布器
           │    └── 相机光学帧    需由实际相机驱动/机器人描述补齐
           └── imu_link         limo_start 的静态发布器
```

`odom → base_link` 的实现见 [底盘驱动 TF 发布段](../limo_base/src/limo_driver.cpp#L585)。发布 `/odom` 消息不等同于发布这条 TF；`pub_odom_tf=false` 时可能出现“话题有数据、TF 却断开”。

- **基础层**不负责生成 `map`，只启动基础层时没有 `map → odom` 是正常的。
- **Cartographer**使用本包 Lua 中的 `published_frame=odom` 和 `provide_odom_frame=false`，意图发布 `map → odom`，把 `odom → base_link` 留给底盘。
- **AMCL**在静态地图方案中根据激光、已有地图和里程计定位，配置 `tf_broadcast=true` 时承担全局定位 TF。
- **RTAB-Map**方案意图由其建图/定位提供全局关系，但相关实现和默认参数在外部包，需运行时验证发布的 frame 和 authority。

实际激光 frame 若是 `laser_frame`，TF 树末端必须与它连通。基础入口只发 `laser_link` 并不能自动连接两个不同名称。相机只有 `camera_link` 也不足以保证 RGB/depth 的 optical frame 已连通。

本包没有实际启动 EKF/`robot_localization`。Cartographer 入口现在默认加载显示 URDF 并启动 `robot_state_publisher`；它只增加 `base_link` 下的 `limo_visual_*` 部件 TF，不修改原有底盘和传感器 TF。其他 YAML 中的同名参数段仍不等于启动动作。

## 6. Cartographer：从扫描匹配到二维栅格

[cartographer.launch.py](launch/cartographer.launch.py#L28) 的关系是：

```text
/scan、/odom、TF
        ↓
cartographer_ros/cartographer_node
        ├── 全局定位 TF、轨迹与子地图
        └── occupancy_grid_node → 二维 OccupancyGrid
                                   ↓
                              demo_2d.rviz
```

它不 include 基础启动，必须先有传感器与里程计。默认 `use_sim_time=false`；配置目录是包安装路径下 `config_files/`，`configuration_basename=limo_lds_2d.lua`；栅格默认 `resolution=0.05` m，`publish_period_sec=1.0` s。

`use_robot_model=true` 时还包含 `limo_model.launch.py`，发布 `/robot_description`、
`/joint_states` 和车体/四轮 TF。关节状态用于默认姿态显示，不代表真实编码器反馈。
模型沿用车端外部 `limo_description` 包的外观资源，说明见 [ROBOT_MODEL.md](ROBOT_MODEL.md)。

[occupancy_grid.launch.py](launch/occupancy_grid.launch.py#L23) 只是 `cartographer_ros/occupancy_grid_node` 的包装。它不从零开始运行 SLAM，也不负责自动保存地图。

### 6.1 Lua 参数应怎样读

来源：[config_files/limo_lds_2d.lua](config_files/limo_lds_2d.lua#L20)。

| 参数 | 源码值 | 阅读重点 |
| --- | --- | --- |
| `map_frame` | `map` | 全局地图坐标系 |
| `tracking_frame` / `published_frame` / `odom_frame` | 都是 `odom` | `tracking_frame` 也写成 `odom` 较特殊，需结合真实 TF 核验，不能默认为 `base_link` 或 IMU |
| `provide_odom_frame` | `false` | 不额外构造自己的一段里程计链，配合已有底盘 TF |
| `use_odometry` | `true` | 要消费里程计，而不只是激光 |
| `num_laser_scans` | `1` | 单路激光，未配置点云输入 |
| `MAP_BUILDER.use_trajectory_builder_2d` | `true` | 使用二维轨迹构建器 |
| `TRAJECTORY_BUILDER_2D.use_imu_data` | `false` | 当前 Cartographer 配置不消费 IMU；底盘有 `/imu` 不会自动改变它 |
| `min_range` / `max_range` | `0.1` / `10` m | 建图侧截取的有效距离，不等同于驱动最大量程 |
| `missing_data_ray_length` | `1.0` m | 缺测激光的射线长度配置 |
| `use_online_correlative_scan_matching` | `true` | 开启在线相关扫描匹配 |
| `motion_filter.max_angle_radians` | `math.rad(0.1)` | 位姿变化筛选阈值，应结合地图更新与计算负载理解 |
| `constraint_builder.min_score` / `global_localization_min_score` | 都是 `0.7` | 约束与全局匹配评分门槛 |

`include "map_builder.lua"` 和 `include "trajectory_builder.lua"` 引用外部 Cartographer 提供的配置，本包没有这两个基础 Lua 文件。

### 6.2 `slam_box.yaml` 是另一种算法的配置

[config_files/slam_box.yaml](config_files/slam_box.yaml) 属于 `slam_toolbox`：`mode=mapping`、`odom_frame=odom`、`map_frame=map`、`base_frame=base_link`、`scan_topic=/scan`，分辨率 `0.05` m，地图更新间隔 `1.0` s，TF 发布周期 `0.02` s，`max_laser_range=50.0` m，最小移动/转角阈值均为 `0.5`。

它还设置 Ceres 求解器、扫描匹配和回环参数。但本包全部 launch 中没有加载它，也没有启动 `slam_toolbox`。修改它不会影响当前 Cartographer 链路，50 m 的参数也不表示硬件具备该量程。

## 7. 静态地图 + Nav2：差速和阿克曼入口

### 7.1 默认资源与外部职责

[limo_nav2.launch.py](launch/limo_nav2.launch.py#L12) 和 [limo_nav2_ackmann.launch.py](launch/limo_nav2_ackmann.launch.py#L12) 都 include 仓库外的 `nav2_bringup/launch/bringup_launch.py`，传入 `map`、`use_sim_time`、`params_file`，再启动 RViz，配置也来自外部 `nav2_bringup/rviz/nav2_default_view.rviz`。

| 入口 | 默认地图 | 默认参数 | 本地默认时钟 |
| --- | --- | --- | --- |
| `limo_nav2.launch.py` | [map1021.yaml](maps/map1021.yaml) | [nav2.yaml](param/nav2.yaml) | `false` |
| `limo_nav2_ackmann.launch.py` | [map1021.yaml](maps/map1021.yaml) | [nav2_ackermann.yaml](param/nav2_ackermann.yaml) | `false` |

文件名的实际拼写是 `ackmann`，不是 `ackermann`。两个入口都不启动底盘和雷达；应先验证基础层，再选择一个导航入口。该外部 bringup 通常负责 map server、AMCL、导航服务器和生命周期管理，但它的实际源码不在本仓库，是否启动 SLAM、组合节点、哪些默认节点等，必须检查车端安装版本。

YAML 中的 `map_server.yaml_filename` 仍常写着 `turtlebot3_world.yaml`。外部 Nav2 launch 通常会将传入的 `map` 重写为实际地图路径。因此不能仅凭这个字面量断定启动加载了 TurtleBot 地图，应看运行中 `/map_server` 的最终参数。

### 7.2 差速 `nav2.yaml` 的关键参数

| 参数路径 | 值 | 对行为的影响 |
| --- | --- | --- |
| `amcl.robot_model_type` | `differential` | 差速里程计误差模型 |
| `amcl.min_particles` / `max_particles` | `500` / `2000` | 粒子数量范围 |
| `amcl.update_min_d` / `update_min_a` | `0.25` m / `0.2` rad | 触发定位更新的运动阈值 |

| `FollowPath.vx_samples` / `vy_samples` / `vtheta_samples` | `20` / `0` / `40` | 轨迹采样配置，是否接受零横向样本需按具体 DWB 实现核验 |

`max_speed_xy=0.44` 与 `max_vel_x=0.22` 是不同约束，不能把前者直接读成当前直行速度。`trans_stopped_velocity=0.25` 还高于配置的最大前进速度 `0.22`，值得检查 DWB 对“停止”的判定是否符合预期，不能仅根据参数断言实际行为。

### 7.3 代价地图并非 PGM 地图

[nav2.yaml 的 local/global costmap](param/nav2.yaml#L138) 配置：

- 局部代价地图：`global_frame=odom`，3 m × 3 m 滚动窗口，0.05 m 分辨率，更新 5 Hz、发布 2 Hz。
- 全局代价地图：`global_frame=map`，0.05 m 分辨率，更新/发布均为 1 Hz。
- 两者 footprint 都是 `[[0.15,0.10],[0.15,-0.10],[-0.15,-0.10],[-0.15,0.10]]`，描述长 0.30 m、宽 0.20 m 的矩形轮廓，需与实际外廓核对。
- 两者都启用 `/scan` 障碍层和 voxel 层。voxel 层点云话题写死为 `/intel_realsense_r200_depth/points`，本包没有提供这个点云发布者；现场相机话题是否匹配需检查。
- 局部膨胀半径为 `0.02` m，全局为 `0.15` m；数值应结合轮廓、分辨率与实际净空验证。
- 全局 `plugins` 包含 static layer；局部虽有 `static_layer` 参数段，其 `plugins` 列表没有启用这个层。配置块存在不等于插件被装载。

### 7.4 阿克曼 `nav2_ackermann.yaml` 的关键差异

[TEB 参数段](param/nav2_ackermann.yaml#L89) 指定：

| 参数 | 源码值 | 需要理解或核验的地方 |
| --- | --- | --- |
| `FollowPath.plugin` | `teb_local_planner::TebLocalPlannerROS` | 需要兼容 Nav2 的 ROS 2 插件；ROS 1 同名包不能直接替代 |
| `controller_frequency` | `5.0` Hz | 与差速 DWB 的 10 Hz 不同 |
| `max_vel_x` / `max_vel_x_backwards` | `0.2` / `0.3` m/s | 速度配置，不是驱动统一限速 |
| `max_vel_theta` | `0.2` | 角速度约束；输出含义还受下一项影响 |
| `min_turning_radius` / `wheelbase` | `0.4` m / `0.1` m | 驱动头文件中的轴距是 `0.2` m，存在不一致 |
| `cmd_angle_instead_rotvel` | `True` | 按 TEB 常见语义是让 `angular.z` 表示转向角；需核对外部插件实现 |
| `xy_goal_tolerance` / `yaw_goal_tolerance` | `0.2` m / `0.2` rad | 到达容差 |
| `costmap_converter_plugin` | `costmap_converter::CostmapToPolygonsDBSMCCH` | 依赖额外插件 |
| `amcl.robot_model_type` | 仍是 `differential` | 换成阿克曼控制器并未同时换成专门定位模型 |

最重要的接口疑点：底盘 [twistCmdCallback()](../limo_base/src/limo_driver.cpp#L435) 用 `r = linear.x / angular.z` 计算曲率，然后转换成转向角，按的是**角速度输入**。若当前 TEB 实际已将 `angular.z` 转成角度，就会重复转换。RTAB 阿克曼参数却设 `cmd_angle_instead_rotvel=False`，两份配置不能视为等价。源码足以确认配置差异；实际输出语义要进一步检查外部 TEB 源码和 `/cmd_vel`。

此 YAML 还混有 `smoother_server`、`behavior_server`、`nav2_behaviors/DriveOnHeading` 等节点/插件配置，与本包旧入口使用的 `recoveries_server` 结构不同；不能直接认定它全部适配 Foxy。多数节点的 `use_sim_time=True`，controller 本身却是 `False`。外部 launch 如果重写时钟可能消除差异，若直接加载则可能混用时钟，需查看运行参数而非只看文件字面值。

### 7.5 名字带 Foxy 的备用文件并不自动启用

[param/nav2_ackermann_foxy.yaml](param/nav2_ackermann_foxy.yaml) 没有被当前任何 launch 默认选中，需要显式指定 `params_file` 才可能加载。

它使用 TEB，速度配置为 `max_vel_x=0.26`、`max_vel_theta=1.0`，轮廓模型为半径 `0.17` m 的圆，局部 costmap 为 `odom` 坐标系；但至少有这些明确疑点：

- `controller_frequency` 被写成 `ontroller_frequency`，标准参数名不会因此得到期望值。
- 行为树插件列表注释了 `nav2_compute_path_to_pose_action_bt_node`，若选用的 XML 需要 `ComputePathToPose`，需检查是否仍有其他注册来源。
- `controller_server` 和多个节点的 `use_sim_time` 不一致。
- 仍依赖未包含的 ROS 2 TEB、costmap converter，并启用同一个旧点云话题。

所以“文件名包含 Foxy”只是命名，不能当作已经验证可用的兼容性证明。

## 8. RTAB-Map：建图/定位与导航是两层

### 8.1 外层和子入口分别启动什么

[limo_rtab_slam.launch.py](launch/limo_rtab_slam.launch.py) include [rtabmap_rgbd_sync.launch.py](launch/rtabmap_rgbd_sync.launch.py)，再启动加载 `rviz/rtabmap.rviz` 的 RViz。两处都声明了 `localization`，默认 `false`，外层没有通过显式 `launch_arguments` 字典传给子入口；应按 launch context 的实际解析核验最终值，不要假定外层只是建图而无法定位。

子入口的 `generate_launch_description()` 定义共用 `parameters`、`remappings`，再用 `UnlessCondition(localization)` / `IfCondition(localization)` 选择一个 RTAB 节点：

| 分支 | 实际节点与参数 | 使用前提 |
| --- | --- | --- |
| 默认 `localization=false` | `rtabmap_slam/rtabmap`，命令参数 `['-d']` | 意图从头建图；`-d` 在 RTAB-Map 中通常表示删除/重建数据库，使用前核对实际数据库路径并保留需要的旧数据 |
| `localization=true` | 同一可执行程序，无 `-d`；加 `Mem/IncrementalMemory='False'`、`Mem/InitWMWithAllNodes='True'` | 需要已有可用的 RTAB 数据库；本包未指定数据库路径，也没有提供数据库文件 |

二者是互斥条件分支，不应手动各启动一个去提供同一组定位输出。RTAB 数据库与 `maps/*.yaml + *.pgm` 也不是同一种地图资源。

### 8.2 输入话题、同步和参数

来源：[共用参数与 remappings](launch/rtabmap_rgbd_sync.launch.py#L50)。

| 项目 | 源码值 | 作用 |
| --- | --- | --- |
| `frame_id` | `base_link` | 机器人参考系 |
| `subscribe_scan` | `True` | 启用扫描输入，映射至 `/scan` |
| `subscribe_rgbd` | `False` | 并未要求 RTAB 节点订阅打包的 RGBD 输入 |
| `odom` | `/odom` | 使用外部里程计；这里未启动视觉里程计节点 |
| `rgb/image` | `/camera/color/image_raw` | 原始彩色输入映射 |
| `rgb/camera_info` | `/camera/color/camera_info` | 标定参数映射 |
| `depth/image` | `/camera/depth/image_raw` | 深度输入映射，需核验与彩色图像的对齐和 frame |
| `qos` | 默认 `2` | 被用于 `rgbd_sync.qos` 及 RTAB 的 `qos_scan/image/imu`；枚举语义与发布端兼容性按外部版本检查 |
| `Reg/Strategy` / `Reg/Force3DoF` | `'1'` / `'true'` | 按 RTAB 常用语义选择 ICP 配准并限制为平面运动 |

入口总会创建 `rtabmap_sync/rgbd_sync`，设置 `approx_sync=True`。但 RTAB 节点显式 `subscribe_rgbd=False`，且没有将 `rgbd_image` 输出重映射到它，因此不能仅凭文件名画出“所有图像必经 rgbd_sync 再到 RTAB”的链路。要用 `ros2 node info` 确认实际订阅者，检查同步节点输出是否被使用。

该文件开头的 TurtleBot3/Gazebo 示例是历史注释，不是当前动作。当前启动列表没有 TurtleBot3、相机驱动或地图 relay，也没有由这些注释自动生成仿真环境。

### 8.3 RTAB 导航入口不负责启动定位

两个 RTAB 导航包装入口 include 的是外部 **`navigation_launch.py`**，而非静态地图入口的 **`bringup_launch.py`**：

| 入口 | 参数文件 | 前置条件和差异 |
| --- | --- | --- |
| [limo_rtab_nav2_diff.launch.py](launch/limo_rtab_nav2_diff.launch.py) | [nav2_rtab_diff.yaml](param/nav2_rtab_diff.yaml) | DWB 差速导航；已从 YAML 移除 AMCL 段，控制器主要参数与 `nav2.yaml` 一致 |
| [limo_rtab_nav2_ackermann.launch.py](launch/limo_rtab_nav2_ackermann.launch.py) | [nav2_ackermann_rtab.yaml](param/nav2_ackermann_rtab.yaml) | TEB；`cmd_angle_instead_rotvel=False`，轴距仍为 `0.1` m，线形 footprint 改成 `[0,0] → [0.3,0]` |

它们都没有 include `limo_rtab_slam`，也没有启动 AMCL/map server，需要先由定位/建图层提供可消费的地图与 `map → odom`，再启动一套导航侧。

差速入口仍声明默认 `map=maps/map1231.yaml`，仓库中没有这个文件，但 `'map': map_yaml_path` 的传递已注释，因此这属于**未消费的遗留默认值**，不能断言启动必定因缺地图报错。阿克曼入口则连地图参数声明也注释了。RTAB 参数文件中留有 `map_server` 配置段，同样不等于导航侧入口会启动 map server。

RTAB 阿克曼 YAML 同样混有 `smoother_server` / `behavior_server` 和不一致的时钟值，外部插件和 Foxy 兼容性仍需确认。两个 RTAB 导航入口都会再开一个 RViz，若已运行 RTAB 外层入口会出现多个可视化窗口，但这本身不能证明导航成功。

特别检查 `/map`：RViz 和 costmap 期望能消费地图；外部 RTAB 版本实际发布 `/map` 还是命名空间内地图，要通过 topic/node 信息确定。本包没有实际启动注释中的地图 relay。

## 9. 本地拆分定位/导航与 `navigation2` 旧入口

### 9.1 `limo_localization.launch.py`

该文件用 [RewrittenYaml](launch/limo_localization.launch.py#L29) 将 `use_sim_time`、`yaml_filename` 重写进参数，默认 `maps/limo.yaml`、`param/amcl_params.yaml`，默认 `autostart=true`、`use_lifecycle_mgr=true`、空 `namespace`。

它启动 `nav2_amcl/amcl`、`nav2_map_server/map_server`，可选 lifecycle manager 的 `node_names=['map_server','amcl']`。设计上是“定位侧”，不是完整导航。

但 `Node` 被从 `nav2_common.launch` 导入，而不是 `launch_ros.actions`，还使用 `node_executable`、`node_name`、`use_remappings` 等旧形式。外部 Nav2 是否还提供该包装类、是否接受这些关键字，需要按实际版本核验；Python 语法检查通过不能证明导入和动作构造成功。

### 9.2 `limo_navigation.launch.py`

它默认也读取 `amcl_params.yaml`，但创建的是导航侧：

```text
nav2_controller/controller_server
nav2_planner/planner_server
nav2_recoveries/recoveries_server
nav2_bt_navigator/bt_navigator
nav2_waypoint_follower/waypoint_follower
可选 lifecycle_manager_navigation
```

其中 `RewrittenYaml` 重写 `use_sim_time`、`bt_xml_filename`、`autostart`、`map_subscribe_transient_local`，行为树路径来自外部 `nav2_bt_navigator/behavior_trees/navigate_w_replanning_and_recovery.xml`。需要先有基础层和地图/定位来源；只启动这个文件不会生成地图或全局定位。

有三处值得逐行读：

- [remappings 定义](launch/limo_navigation.launch.py#L22)：先把 `remappings` 设为 `LaunchConfiguration`，紧接着覆盖成固定 TF 重映射列表，因此后面同名 launch 参数不是实际开关。
- [recoveries_server](launch/limo_navigation.launch.py#L94) 只接收 `use_sim_time`，没有传 `configured_params`；即使 YAML 中添加恢复行为配置，也不一定进入此节点。
- `namespace` 主要用于参数重写根键和 TF 重映射，节点没有统一传 `namespace=...`。不要直接认定非空 namespace 就具备完整多车隔离。

### 9.3 `limo_start_navigation.launch.py` 当前不能充当总入口

该文件意图同时 include 上述两个文件，将各自 `use_lifecycle_mgr` 设为 `false`，再由一个 manager 管理七个节点；`map` 是必填参数，无默认值。

但 [generate_launch_description() 末尾](launch/limo_start_navigation.launch.py#L93) 在 `ld.add_action(...)` 后没有 `return ld`。静态 AST 检查确认该函数没有任何 `Return`，实际会隐式返回 `None`，ROS launch 得不到预期描述。

此外，它给导航子入口传的是 `use_remappings`，而该子入口声明的是 `remappings`，且又把后者覆盖成常量列表。这组控制并未形成一致接口。即便以后补齐返回值，也应继续验证子入口 API 和参数，不能只补一行就认定整套导航已可用。

### 9.4 `navigation2.launch.py` 的默认参数文件不存在

这个文件默认地图是已有的 [zhiyuan.yaml](maps/zhiyuan.yaml)，但 [params_file 默认值](launch/navigation2.launch.py#L36) 是 `param/navigation2.yaml`，该文件不在当前仓库。

它同样包装外部完整 Nav2 bringup，并不提供基础层。显式指定存在的 `params_file` 可以绕过这个默认缺失项，但剩余依赖与版本兼容性仍需独立验证。它是 `limo_nav2` 的另一种包装选择，不是运行 `limo_nav2` 后的下一步。

## 10. 参数文件怎样关联，哪些只是遗留资源

### 10.1 `amcl_params.yaml` 的结构问题

[param/amcl_params.yaml](param/amcl_params.yaml) 除 AMCL 外还含 map server、planner、BT、controller 和 costmap，名字不能代表其全部内容。

可直接从文本和通用 YAML 解析确认的问题：

1. `amcl.ros__parameters.initial_pose: {0.0,0.0, 0.0, 0.0}` 是 flow mapping 写法。PyYAML 实际解析为 `{0.0: None}`，不是四个数字的列表，也不是 AMCL 的 `x/y/z/yaw` 命名参数。通用 YAML 语法合法不等于 ROS 参数结构合法。
2. [局部 costmap 段](param/amcl_params.yaml#L149) 的 `inflation_layer:` 后没有缩进内容，`cost_scaling_factor: 3.0` 与它同级。实际解析得到 `inflation_layer=None`，缩放参数没有进入预期的层命名空间。
3. costmap 使用 `plugin_names` / `plugin_types`，controller 的 DWB 参数直接放在 `controller_server.ros__parameters` 下，BT 使用 `bt_xml_filename`；而 `nav2.yaml` 使用 `plugins`、`FollowPath` 子命名空间和 `default_bt_xml_filename`。这些结构跨版本混杂，应对照实际 Foxy Nav2 的参数声明，不能直接相互替换。
4. costmap 中的 `use_sim_time=True` 与其他节点为 `False` 混合。该组 launch 会尝试统一重写时钟，但仍需验证最终参数。

这也是为何 [readme.md](readme.md) 中“基础 → 导航 → 定位”的历史命令，只能作为线索：它涉及上述旧入口和旧参数，尚不能当作现成可靠流程。

## 12. scripts：历史启动脚本与硬件实验

这些脚本没有被 CMake 安装成可执行程序，也没有在任何 launch 中启动。它们均不是本包当前的 ROS 2 IMU 数据发布链；`/imu` 来自底盘驱动。

| 脚本 | 真实作用与函数 | 依赖、限制和源码问题 |
| --- | --- | --- |
| [start_build_map_2d_ros2.sh](scripts/start_build_map_2d_ros2.sh) | 用 `roslaunch` 后台运行 `build_map_2d/revo_build_map_2d.launch` 和 `limon_bringup/limon_start.launch`，期间固定 sleep | 名字带 ROS2，实际是 ROS 1 命令和包名；仓库 ROS 2 包是 `limo_bringup`；不应直接作为 Foxy 建图脚本运行 |
| [blinkatest.py](scripts/mpu6050_test/blinkatest.py) | 用 `board`、`busio.I2C(board.SCL, board.SDA)` 测试 I²C 对象创建 | 需要 Adafruit Blinka、兼容的板级引脚支持和 I²C 权限；不是传感器驱动，也不发布 ROS 话题 |
| [simple_test.py](scripts/mpu6050_test/simple_test.py) | 创建 `adafruit_mpu6050.MPU6050`，循环打印加速度、角速度和温度 | 依赖 `board`、`adafruit_mpu6050`；源码注释明确写“各种报错，无法使用”；`gyro` 输出是 rad/s，中文“角加速度”注释不准确；无限循环后的 `done` 正常情况下不可达 |
| [use_smbus.py](scripts/mpu6050_test/use_smbus.py) | `MPU_Init()` 写寄存器，`read_raw_data()` 读 16 位原始数据，循环打印 | 总线写死为 1、地址 `0x68`；写 `GYRO_CONFIG=24` 选择的量程与后面 `/131.0` 的 ±250°/s 比例不符；有符号转换的边界和减数有错误 |
| [use_smbus_2.py](scripts/mpu6050_test/use_smbus_2.py) | `mpu6050` 类实现量程、温度、加速度和陀螺仪读取 | 同样写死总线 1；`get_all_data()` 内部少写 `self.`；主循环每秒重新构造并唤醒传感器；不提供 ROS 消息 |

两个具体问题值得作为学习练习：

- `use_smbus.py:read_raw_data()` 写的是 `if value > 32768: value -= 65535`。16 位二补码应在 `>= 0x8000` 时减 `65536`，当前实现会把 `0x8000` 当作正数，其他负数也偏 1。
- `use_smbus_2.py:get_all_data()` 调用 `get_temp()`、`get_accel_data()`、`get_gyro_data()`，没有 `self.`，调用该方法时会尝试查找未定义的全局函数。其主循环没有调用 `get_all_data()`，所以该缺陷不一定在直接运行脚本时首先暴露。

不要为检查语法而 import 这些脚本：`use_smbus.py` 顶层会打开总线、写寄存器并进入无限循环；`use_smbus_2.py` 在类定义时就执行 `smbus.SMBus(1)`。静态检查应读取文本后 `ast.parse()`，不能把语法检查变成硬件操作。

## 14. 源码问题清单与逐项验证办法

以下先区分已能由文件确认的事实，再列现场核验点。本文只做静态检查，没有执行表中的 ROS 命令或修改这些问题。

| 问题 | 能确认的事实/影响边界 | 后续验证办法 |
| --- | --- | --- |
| 基础入口隐藏依赖 | `rf2o` share 查询未注释，include 已注释 | `ros2 pkg prefix rf2o_laser_odometry`；再对基础入口执行 `--show-args` 看是否在描述生成时失败 |

| 激光 frame/参数路径有两套 | 主入口静态 `laser_link`，另一路本地 YAML 是 `laser_frame` | 查实际雷达参数、`/scan` 的 frame，再 `tf2_echo base_link <实际frame>` |
| 聚合 launch 缺返回 | `limo_start_navigation.generate_launch_description()` 没有 `return` | AST 可确认；ROS 环境中 `--show-args` 仍需先满足 import/包查找，可能先遇到其他错误 |
| `navigation2.yaml` 缺失 | 默认路径所指文件不存在 | 用安装路径 `test -f` 检查；换参数之前核对配置对应的 Nav2 版本 |

| 旧 `Node` 导入和参数 | 本地定位使用 `nav2_common.launch.Node` 及旧关键字 | 在车端确认该符号是否可导入，查看 `--show-args` traceback，并核对实际 `nav2_common` 来源 |
| `initial_pose` 与空 inflation 层 | 通用 YAML 解析分别得到 `{0.0: None}`、`None` | 先检查结构，再用对应 ROS 版本参数解析/启动日志；语法成功不代表可被 ROS 接受 |
| 阿克曼配置/驱动语义不一致 | `cmd_angle_instead_rotvel=True/False` 两套值，TEB 轴距 0.1 m、驱动 0.2 m | 查看外部 TEB 当前实现，观测 `/cmd_vel` 单位与驱动转换，随后受控验证曲率 |
| Foxy 与新版本配置混杂 | `recoveries_server` 与 `behavior_server`/smoother 并存于不同方案 | 查 Nav2 包版本、插件导出 XML、实际启动列表与生命周期，不能靠文件名判断兼容 |
| 参数拼写与加载关系 | 备用文件有 `ontroller_frequency`；`repeat_rate` 的传参代码被注释；若干配置无入口加载 | 查看实际 `ros2 param list/get` 和 launch 的 `parameters`，确认修改是否进入节点 |
| RTAB 同步链未明确使用 | 启动 `rgbd_sync`，RTAB 却 `subscribe_rgbd=False` | `ros2 node info` 看 RGBD 输出订阅者和原图输入，核对彩深同步及 QoS |

### 14.1 先检查安装空间和描述，再启动硬件

以下供具备 Foxy 环境的 Linux 终端后续使用。每个终端先 source 同一个工作区，确保没有混入 ROS 1 或另一份同名包：

```bash
echo "$ROS_DISTRO"
ros2 pkg prefix --share limo_bringup
ros2 pkg prefix --share limo_base
ros2 pkg prefix --share nav2_bringup
ros2 pkg prefix --share ydlidar_ros2_driver
ros2 pkg prefix rf2o_laser_odometry

bringup_share="$(ros2 pkg prefix --share limo_bringup)"
test -f "$bringup_share/maps/map1021.yaml"
test -f "$bringup_share/param/nav2.yaml"
test -f "$bringup_share/param/navigation2.yaml"

ros2 launch limo_bringup limo_start.launch.py --show-args
ros2 launch limo_bringup limo_nav2.launch.py --show-args
```

`--show-args` 用于加载启动描述并列参数，仍会触发 `get_package_share_directory()` 等解析，不等同于纯文本语法检查；它通过也不能证明硬件或导航算法正常。第三个 `test -f` 按当前源码预期找不到文件，目的是核对缺失项，而不是要求三个检查都成功。

### 14.2 基础层运行后的观测点

先确认选择了一套硬件入口，再在观察终端检查：

```bash
ros2 node list
ros2 topic list -t
ros2 topic info /scan --verbose
ros2 topic echo /scan
ros2 topic echo /odom
ros2 topic echo /limo_status
ros2 run tf2_ros tf2_echo odom base_link
ros2 run tf2_ros tf2_echo base_link laser_link
```

若实际扫描 frame 是 `laser_frame`，最后一条改为该 frame。`topic echo`、`tf2_echo` 会持续输出，每条检查后用 Ctrl+C 结束再执行下一条，或分别放在观察终端，不要当成会自动执行完的一组脚本。

还要核对话题时间戳和频率，确认里程计、激光和 TF 都在更新。基础层检查通过后，才选择上层方案；此阶段缺 `map` 不应立即当成底盘失败。

### 14.3 按方案分开验证上层

| 所选方案 | 必须先具备 | 选择该方案后的主要检查 | 不应同时额外启动 |
| --- | --- | --- | --- |
| Cartographer 建图 | 基础输入、连通的雷达和里程计 TF、Cartographer 外部依赖 | `cartographer_node` / `occupancy_grid_node`、栅格数据、`map → odom`、时间戳 | AMCL、另一个提供全局 TF 的 RTAB 实例、重复 occupancy-grid |
| 静态地图 Nav2 | 基础层、匹配现场的 YAML/PGM、对应 Nav2/控制插件 | map server 最终路径、AMCL 初始位姿、所有必要 lifecycle 节点 active、导航 action | RTAB 导航侧包装、本地拆分 Nav2、第二套完整 Nav2 |
| RTAB 建图/定位 + 导航 | 基础层、相机输入/TF、同步与 QoS、定位时所需数据库 | 先核验 RTAB 地图和全局 TF，再启动一套 RTAB 导航侧；确认地图话题接入 costmap | AMCL/map server 默认定位链、另一个 SLAM 全局 TF 来源、重复 RTAB 子入口 |
| 本地拆分定位 + 导航 | 先解决旧 API、YAML 结构与版本兼容，再有基础层 | 独立确认定位侧 active 和 TF，再确认导航侧 active；使用各自 manager 或一个统一 manager | 完整 Nav2 包装入口、重复管理相同节点的生命周期管理器 |

例如静态地图方案运行后，可用下列查询确认**最终生效值**，无需发送运动命令：

```bash
ros2 run tf2_ros tf2_echo map odom
```

节点名称与命名空间按现场调整。`ros2 action list` 中有导航动作、RViz 里有地图，仍只是接口检查；目标点可达性、避障、转弯半径、停车和恢复行为需要后续实车验证。

## 15. 建议的学习顺序

1. **先理解资源包。** 对照 `package.xml`、`CMakeLists.txt`、`setup.py`，解释为什么本包主要用 `ros2 launch`，以及源码目录与安装 share 的差异。
2. **画基础动作列表。** 读 `limo_start.generate_launch_description()`，区分立即执行的包查找、只构造但未加入列表的 `pub_tf`、被注释的 include、实际返回的动作。
3. **追到底盘接口。** 沿 `limo_base.launch.py → LimoDriver → twistCmdCallback()`，理解 `/cmd_vel`、运动模式、`/odom` 和 TF 的关系。
4. **只选一条建图链阅读。** 先读 Cartographer 父/子入口和 Lua，确认谁提供 `map → odom`；再把 `slam_box.yaml` 作为未接入的另一种方案对照。
5. **逐层读差速 Nav2 参数。** 按 AMCL → BT → planner → controller → local/global costmap 阅读 `nav2.yaml`，分别记录输入、输出、坐标系和外部插件。
6. **比较阿克曼，而非只换文件名。** 对照 `nav2_ackermann.yaml`、`nav2_ackermann_rtab.yaml`、备用 Foxy 文件和驱动曲率公式，核对轴距、输出单位、原地转向恢复与机械约束。
7. **再读 RTAB 条件分支。** 解释 `localization`、`-d`、数据库、`subscribe_rgbd` 与同步节点的关系，最后追踪地图如何交给仅导航侧入口。
8. **用旧入口练习定位错误。** 从缺 `return ld`、旧 Node 导入、YAML 结构、未消费参数入手，学习区分“语法正确”“参数有效”“运行正常”和“实车验证通过”。
