# set_nav_point 代码解析

> 分析日期：2026-11-24。已逐一读取本包 `package.xml`、`CMakeLists.txt`、全部 C++ 和 Python 文件；当前没有 `.h`、`.launch` 或 `.yaml` 文件。本文是静态源码分析，未编译、未执行脚本、未连接机械臂、未做实车验证。

## 1. 职责和真实包名

[package.xml](package.xml) 的真实包名和 [CMakeLists.txt](CMakeLists.txt) 的工程名均为 `set_nav_point`。本包包含三份独立程序：

| 程序 | 职责 | 运行方式在构建中的状态 |
| --- | --- | --- |
| [set_point_to_move_base.cpp](src/set_point_to_move_base.cpp) | 向 `move_base` 顺序发送两个固定点 | 已声明 C++ 可执行目标 |
| [more_task_node.py](script/more_task_node.py) | 起点执行取放准备，导航后投放，再尝试返回原点 | 只有源码，没有 Python 安装规则；成功路径存在阻塞问题 |
| [more_task_loop_node.py](script/more_task_loop_node.py) | 在四个固定导航点之间循环，到前三个点执行机械臂动作 | 只有源码，没有 Python 安装规则 |

三个程序都把全局路径规划和底盘运动交给外部 `move_base`。Python 通过 `pymycobot` 直接访问机械臂串口，没有使用 MoveIt 或 ROS 机械臂 action。文件顶部“目标点夹取、返回起点”等注释不完全等于当前实际执行流程，下面以代码分支为准。

## 2. 阅读顺序与构建事实

建议依次阅读：

1. [package.xml](package.xml)：依赖清单与真实包名。
2. [CMakeLists.txt](CMakeLists.txt)：过滤模板注释，只看启用的构建命令。
3. [src/set_point_to_move_base.cpp](src/set_point_to_move_base.cpp)：理解 action 客户端的基本发送与等待。
4. [script/more_task_node.py](script/more_task_node.py)：把导航结果分支与机械臂动作连接起来，注意 `rospy.spin()`。
5. [script/more_task_loop_node.py](script/more_task_loop_node.py)：区分三个动作函数、四个导航目标和 99 次循环。

构建文件中的有效内容为：

- `find_package(catkin REQUIRED COMPONENTS actionlib move_base_msgs roscpp rospy)`。
- `catkin_package()` 没有导出库、头文件或显式依赖列表。
- **唯一的 C++ 可执行目标是 `set_point_to_move_base`**，输入为 `src/set_point_to_move_base.cpp`，链接 `${catkin_LIBRARIES}`。
- C++11 编译选项、示例库、消息/服务/action 生成和测试目标均未启用。
- `catkin_install_python()`、`install(TARGETS ...)` 等安装段全部是模板注释，两个 Python 文件没有被列为安装程序，C++ 目标也没有安装规则。

标准 catkin devel 构建成功后，C++ 可执行文件通常位于 `devel/lib/set_nav_point/set_point_to_move_base`。仅使用 install 空间时，不能假设这些程序已经安装。

`package.xml` 声明了 `actionlib`、`move_base_msgs`、`roscpp`、`rospy`，没有声明 Python 任务额外需要的 `pymycobot`。源码存在并不表示当前机器已经具备机械臂 Python 库、串口权限和兼容解释器。

## 3. 三个程序共有的 action 逻辑

默认 ROS 节点名均为 `simple_navigation_goals`，action 名均为相对名称 `move_base`。无命名空间时对应 `/move_base`，目标坐标系均为 `map`。

典型流程为：

```text
建立 action 客户端 → 等待服务器 → 发送一个目标
    → 等待该目标结果 → 判断是否 SUCCEEDED → 执行后续阶段
```

结果判断只区分 `SUCCEEDED` 与其他状态，没有完整处理 `ABORTED`、`PREEMPTED`、`REJECTED` 等状态；`waitForResult()` / `wait_for_result()` 都没有任务时限。任务失败通常只打印日志，然后继续下一阶段。

### 同名 goal、ROS 节点名和任务状态的区别

- 每个文件里的 `goal1` 等变量都是该程序的局部对象，同名不代表共享目标或同一个请求。
- actionlib 在每次发送时维护独立的 action goal ID；`getState()` / `get_state()` 对应当前客户端跟踪的目标。
- `/move_base/status` 中可能同时有多个历史或其他客户端的状态，调试应关联 `goal_id`，不能固定取列表第一个元素。
- 同一命名空间内同时启动这些程序，或启动邻包 `multipoint_navigation` 的同名示例，会发生 `simple_navigation_goals` 节点重名冲突。
- 单独改节点名也不等于允许多个调度器共同控制一个 `move_base`；新目标仍可能抢占正在执行的目标。

## 4. C++：set_point_to_move_base.cpp

### 4.1 执行顺序和固定点来源

程序创建 `SimpleActionClient<MoveBaseAction>("move_base", true)`，第二个参数开启内部 spinning 线程，因此主函数不用另行 `ros::spin()` 来接收结果。

它每次等待服务器 5 秒，失败则继续等待。服务可用后，按顺序执行：

| 阶段 | 目标变量 | `map` 下的 `(x, y)` / m | 四元数 `(x, y, z, w)` | 完成后行为 |
| --- | --- | --- | --- | --- |
| 1 | `goal1` | `(1.0, 2.0)` | `(0, 0, 0, 1)` | 打印结果，继续第二点 |
| 2 | `goal2` | `(3.0, 4.0)` | `(0, 0, 0, 1)` | 打印结果，进程退出 |

目标坐标全部硬编码，`position.z` 使用默认值 0；每个目标在发送前设置当前 ROS 时间。尽管文件注释提到 RViz 的 `2D Nav Goal`，实际代码**没有订阅 `/move_base_simple/goal`，没有接收 RViz 点击点**。

### 4.2 状态处理

每次 `sendGoal()` 后调用无限等待的 `waitForResult()`，再通过 `getState() == SUCCEEDED` 打印日志。第一点失败也发送第二点；没有失败计数、重试、取消或中止逻辑，进程退出码始终为 0。

服务等待循环条件也没有检查 `ros::ok()`。`ros::NodeHandle nh` 被创建但没有用于读取参数。程序没有机械臂控制逻辑。

## 5. Python 单次任务：more_task_node.py

### 5.1 初始化有硬件副作用

文件导入 `rospy`、`actionlib`、`MoveBaseAction` / `MoveBaseGoal`、`pymycobot.mycobot.MyCobot`、`time` 和未使用的 `pymycobot.genre.Angle`。

`mc = MyCobot("/dev/ttyACM0", 115200)` 位于模块顶层，**在 `rospy.init_node()` 之前就初始化机械臂串口对象**；直接导入文件也会触发这一步。不能通过 import 来无副作用地检查函数。

shebang 为 `#!/usr/bin/env python`，ROS Noetic 下应核对实际解释器；串口设备、波特率和依赖全部写死，没有参数化。

### 5.2 两个机械臂动作函数

`send_angles()` 的数组是六关节目标角，数值按该 API 的关节角语义解释；第二个参数是该 API 的速度参数，不是代码注释所说的笛卡尔 `mm/s`。实际设备型号、速度范围和夹爪状态约定需要单独核对。

| 函数 | 实际调用顺序 |
| --- | --- |
| `target_1()` | `[0, 0, 0, 0, 0, 0]`、速度 50 → 等待 3 s → `[-3.42, -104.76, -31.28, 46.31, -0.26, 46.23]`、速度 50 → 等待 3 s → `set_gripper_state(1, 80)` → 等待 3 s → `[83.05, -103.53, 143.87, -72.15, 3.25, 46.49]`、速度 50 → 等待 5 s |
| `target_2()` | 等待 1 s → `[92.02, -39.99, -31.46, 52.73, -2.02, 46.14]`、速度 50 → 等待 3 s → `set_gripper_state(0, 80)` |

本例把夹爪状态 1 用作合拢、0 用作打开。函数只有发送命令和固定墙钟时间 sleep，没有检查机械臂是否到位、抓取是否成功或串口返回值。

### 5.3 真实任务流程与阻塞问题

```text
等待 move_base 可用（无时限）
    ↓
在当前位置执行 target_1()，没有先导航到取物点
    ↓
发送 goal1：map 下 (1.3, -1.06)，四元数 (0, 0, 0, 1)
    ↓ 等待结果
成功：执行 target_2() → rospy.spin() 持续等待关闭
失败：记录失败 → 继续到下方返回目标代码
    ↓
下方代码定义 goal2：(0, 0)，四元数 (0, 0, 0, 1)，发送并等待
```

**关键问题是成功分支里的 `rospy.spin()`。** 在正常运行、不关闭 ROS 的情况下，它不会返回，所以成功投放后无法继续执行下方 `goal2` 的返程代码。反而是第一目标失败时，可以直接进入返程代码。关闭 ROS 后也不应把 spin 返回后继续执行代码视为正常返程机制，后面没有停机条件保护。

`goal2` 的 `(0, 0)` 是硬编码的 `map` 原点，并非启动时保存的机器人位置。源码没有任何读取并记录“起点”的过程。

## 6. Python 循环任务：more_task_loop_node.py

### 6.1 与单次脚本的区别

shebang 为 `#!/usr/bin/env python3`，同样在模块顶层创建 `/dev/ttyACM0`、115200 波特率的 MyCobot 对象。它实际是“导航到预设点后执行关节动作和灯光演示”，**没有调用夹爪接口**，不能仅凭顶部注释认定它实现了抓取投放。

三个动作函数如下；数组均为六关节目标角，sleep 使用墙钟时间：

| 函数 | 动作与重复方式 |
| --- | --- |
| `point_1()` | 内部重复 2 次：`[-1.49, 115, -153.45, 30, -33.42, 0]`、速度 80，灯光 `(0,0,50)`，等 1 s；再到 `[-1.66, 50.53, -130.16, 123.66, -2.63, 0]`、速度 80，灯光 `(0,50,0)`，等 1 s；再将末关节分别设为 50 和 -50，每步等 3.5 s |
| `point_2()` | 先到 `[-95.88, -76.81, 107.75, 61.87, 5.44, 88.85]`、速度 60，等 2 s；内部重复 2 次，将第四关节依次设为 61.87、-30.49、61.87，其余同上，每步等 1.5 s |
| `point_3()` | 先发送 `[38.14, -108.01, 123.57, -12.74, 52.91, 1.23]`、速度 60；内部重复 2 次，在该角度数组和 `[-4.04, 125.41, -115.48, -32.43, 88.94, -24.6]` 之间切换，每步等 3 s |

这些动作依赖固定关节角与固定等待时间，不是基于视觉、运动规划或到位反馈的动作算法。

### 6.2 四个固定导航点

四个目标都在进入外层循环前构造一次，坐标和姿态来自源码字面量，不从文件、参数、RViz 或实际初始位姿读取。

| 目标 | `map` 下 `(x, y)` / m | 四元数 `(x, y, z, w)` | 成功后的动作 |
| --- | --- | --- | --- |
| `goal1` | `(1.63, 0.1)` | `(0, 0, -0.0264309, 0.999651)` | `point_1()`，再等 5 s |
| `goal2` | `(0.85598, -0.74)` | `(0, 0, -0.709988, 0.704214)` | `point_2()`，再等 5 s |
| `goal3` | `(0.26, -0.78)` | `(0, 0, 0.999895, -0.0144663)` | `point_3()`，再等 5 s |
| `goal4` | `(0, 0)` | `(0, 0, 0, 1)` | 只等 3 s，没有 `point_4()` |

前三个姿态不全是“朝正方向”；应以四元数为准。`goal4` 同样是地图原点，不是采集到的启动位置。

### 6.3 外层循环与状态处理

`loop_num = 99`，每轮先减 1，然后完整执行 `goal1 → goal2 → goal3 → goal4`。在所有等待均正常返回的情况下，最多发送 `99 × 4 = 396` 次导航目标。

每段只有到达 `SUCCEEDED` 时才执行该点机械臂动作和后续 sleep；失败时打印日志并继续下一个点，不重试、不停止整轮。等待结果没有时限，一个目标不结束就会阻塞后续所有任务。

目标对象的 `target_pose.header.stamp` 在进入 99 次循环之前设置，后续重发时没有刷新。每次 action 请求仍由 actionlib 维护新的 goal ID，但目标位姿时间戳会一直沿用旧值；长期运行时应检查服务端是否需要查询旧时刻 TF，不能把新 action ID 当作已更新时间戳。

循环条件只有 `loop_num > 0`，没有 `rospy.is_shutdown()`；脚本没有注册停机时的 `cancel_goal()`、机械臂停止或资源清理回调。

## 7. Topic、action、串口和参数接口

无命名空间时，三个客户端都通过 actionlib 使用：

| 方向 | 接口 | 类型/说明 |
| --- | --- | --- |
| 发送目标 | `/move_base/goal` | `move_base_msgs/MoveBaseActionGoal` |
| action 取消通道 | `/move_base/cancel` | `actionlib_msgs/GoalID`；源码没有主动调用取消 |
| 接收状态 | `/move_base/status` | `actionlib_msgs/GoalStatusArray` |
| 接收反馈 | `/move_base/feedback` | `move_base_msgs/MoveBaseActionFeedback`；程序没有自定义反馈处理 |
| 接收结果 | `/move_base/result` | `move_base_msgs/MoveBaseActionResult` |
| Python 直接硬件访问 | `/dev/ttyACM0` | MyCobot 串口，115200 波特率 |

本包没有直接发布 `/cmd_vel`，没有自己读取 TF，没有 RViz 选点订阅，没有 service、自定义 action 定义或业务文件读写。ROS 和串口库自身的系统访问不等于本包实现了目标文件接口。

三个文件都没有 ROS 参数读取。坐标、姿态、节点名、action 名、串口、波特率、关节角、动作速度、sleep 时长和循环次数均为硬编码默认常量；向参数服务器设置同名字段不会自动改变它们。

## 8. 启动前提和当前可用入口

共有前提是：ROS 1 环境与依赖、ROS master、可用的 `move_base` action server，以及外部地图/定位、TF、传感器、规划和底盘控制链路。导航栈应先能独立完成单点导航，再讨论本包的顺序任务。

成功编译并加载 devel 环境后，当前 CMake 已声明的 C++ 入口为：

```bash
rosrun set_nav_point set_point_to_move_base
```

该命令会立即发送硬编码目标，本文未执行。包内没有可直接调用的 launch 文件。

Python 文件没有被 `catkin_install_python()` 或 `install(PROGRAMS ...)` 启用为安装入口，因此本文不提供“编译完就可用”的脚本 `rosrun` 命令。实际使用前还需要确认：

- 与 ROS 环境匹配的 Python 解释器，及可导入的 `rospy`、`actionlib`、`move_base_msgs`、`pymycobot`。
- 机械臂型号/API 兼容、`/dev/ttyACM0` 确实为该机械臂、115200 波特率正确且当前用户有访问权限。
- 当前地图中的固定点可达，机械臂角度和动作区域与实际硬件及周边空间相符。
- 将纯导航问题和机械臂任务问题分开检查；仅把 action 重映射到仿真并不会阻止 Python 脚本访问真实串口。

## 9. 代码可证的问题与调试检查

| 问题 | 源码证据 | 调试关注点 |
| --- | --- | --- |
| “RViz 选点”描述与实现不符 | C++ 目标完全硬编码 | 运行结果不随 RViz 选点变化 |
| 成功投放后不正常返程 | 单次脚本在成功分支执行 `rospy.spin()` | 返程代码位于 spin 后方 |
| 地图原点被当成起点 | 两个 Python 返程点都是 `(0, 0)`，没有初始位姿采集 | 换地图或换启动位置后需重新核对 |
| 多程序共用节点名 | 都调用 `simple_navigation_goals` | 检查 `/rosout` 是否报告重名关闭 |
| 导航失败只记日志 | 多个 else 后继续下一阶段 | 日志“程序完成”不等于任务成功 |
| 动作缺少反馈 | 发送角度/夹爪命令后只 sleep | 固定等待不能证明到位或抓取成功 |
| 脚本导入就访问硬件 | `mc = MyCobot(...)` 位于顶层 | 不通过直接 import 做静态检查 |
| 依赖与安装不完整 | 缺 `pymycobot` 清单和 Python 安装规则 | 分开核对 Python 环境和 CMake 产物 |
| 目标时间戳未刷新 | 循环前创建目标，循环内反复 send | 区分位姿 stamp 与 action goal ID |
| 没有超时/取消/停机策略 | 无限等待、无 cancel、无 shutdown hook | 先在隔离测试环境验证异常分支 |

建议先做只读诊断，本文没有执行这些命令：

```bash
rospack find set_nav_point
rosnode list
rostopic info /move_base/goal
rostopic echo /move_base/status
rostopic echo /move_base/result
rosrun tf tf_echo map base_link
ls -l /dev/ttyACM0
```

阅读日志时记录“脚本名、轮次、目标序号、实际坐标、goal ID、终态、是否进入动作函数”，避免不同程序里相同的 `Sending goal 1` 被混在一起。先在模拟 action server 和机械臂替身环境中验证成功、失败、超时与关闭分支，再决定实车调试方案；这些验证尚未在本次完成。
