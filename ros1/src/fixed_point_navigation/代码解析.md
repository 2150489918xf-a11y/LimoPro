# fixed_point_navigation 目录代码解析：真实包名 multipoint_navigation

> 分析日期：2026-11-24。本文已读取本目录的 `package.xml`、`CMakeLists.txt`、全部 C++ 和 Python 源码；当前没有 `.h`、`.launch` 或 `.yaml` 文件。结论来自静态分析，未编译、未启动导航、未做实车验证。

## 1. 包名、职责与边界

**目录名是 `fixed_point_navigation`，真实 ROS 包名是 `multipoint_navigation`。** [package.xml](package.xml) 的 `<name>` 和 [CMakeLists.txt](CMakeLists.txt) 的 `project()` 都使用后者。包清单里的 description 仍写着 `set_nav_point`，这是遗留描述，不是包名。

本包提供向 ROS 1 `move_base` action server 发送预设目标的示例：

- C++ 版：顺序发送源码内定义的目标并等待结果；实际发送顺序为目标 1、目标 2、再次目标 2。
- Python 版：顺序发送两个固定目标，中间暂停 4 秒。

它们负责目标调度，路径规划、障碍处理、速度控制由外部 `move_base` 导航栈和底盘承担。源码没有 RViz 目标点订阅、交互式选点、参数读取或目标点文件加载。

## 4. C++ 版：逐阶段解析

入口是 [multipoint_navigation.cpp](src/multipoint_navigation.cpp) 的 `main()`，没有自定义类或路径搜索算法。

### 4.1 初始化与服务等待

```text
初始化节点 simple_navigation_goals
    ↓
创建 SimpleActionClient<MoveBaseAction>("move_base", true)
    ↓
每次等待 5 秒，直到 action server 可用
```

第二个构造参数 `true` 启用 action 客户端的内部 spinning 线程，因此结果接收不依赖主函数调用 `ros::spin()`。`ros::NodeHandle nh` 被创建，但没有用来读取参数或建立普通话题接口。

服务等待循环没有 `ros::ok()` 条件，服务长时间不可用时会持续重试；停机响应需要结合 actionlib 的行为检查，不能把这个循环当作完整的退出控制。

### 4.2 固定目标的真实来源与顺序

全部位置和四元数都是源码字面量；不是从当前机器人位置、地图文件、RViz 或 YAML 读取。平面位置单位为米，坐标系固定为 `map`，`position.z` 使用消息默认值 0。

| 实际发送次数 | 实际发送变量 | `(x, y)` | 四元数 `(x, y, z, w)` | 说明 |
| --- | --- | --- | --- | --- |
| 第 1 次 | `goal1` | `(1.07, 0.31)` | `(0, 0, 0, 1)` | 朝向为 map 的正 X 方向 |
| 第 2 次 | `goal2` | `(3.0, 4.0)` | `(0, 0, 0, 1)` | 第二个固定点 |
| 第 3 次 | 仍是 `goal2` | `(3.0, 4.0)` | `(0, 0, 0, 1)` | 创建了 `goal3`，后续却全部填写、发送 `goal2` |

第三阶段中的 `goal3` 既没有被正确填充，也没有被发送。日志继续输出 `Sending goal 2`。因此不能把本程序描述成已经实现三个不同目标点的巡航。

`goal1` 和 `goal2` 在各自发送前设置时间戳；第三阶段重新给 `goal2` 设置时间戳。每次 `sendGoal()` 是新的 action 请求，即使目标位置一样，也不是恢复之前的请求。

### 4.3 等待和结果处理

每次发送后调用不带时限的 `ac.waitForResult()`，然后检查 `ac.getState()`：

- `SUCCEEDED`：打印到达日志。
- 其他状态：统一打印失败日志；没有区分 `ABORTED`、`REJECTED`、`PREEMPTED` 等。
- 无论前一个目标成功或失败，都继续后面的发送阶段；没有重试、跳过规则、错误退出或主动取消。

第一阶段之后的 `ros::Duration(7);` **只构造一个时长对象，没有调用 `.sleep()`**，所以不会暂停 7 秒。最后一个阶段结束后进程返回 0，返回码也没有反映导航是否失败。

## 5. Python 版：流程与 C++ 的区别

[multipoint_navigation.py](script/multipoint_navigation.py) 是另一个独立程序，不是 C++ 节点的配置文件，也不是其自动回退方案。

```text
初始化 simple_navigation_goals
    ↓
创建 move_base 客户端
    ↓
仅等待服务 5 秒，不检查是否等到
    ↓
发送 goal1 (1.0, 2.0)，无限等待结果并记录成功/失败
    ↓
time.sleep(4)
    ↓
发送 goal2 (3.0, 4.0)，无限等待结果并记录成功/失败
    ↓
结束
```

两个目标均使用 `map`、`orientation.w = 1.0`，其余姿态分量默认 0；每个目标在构造时设置当前 ROS 时间。**Python 第一个点 `(1.0, 2.0)` 与 C++ 第一个点 `(1.07, 0.31)` 不相同。** Python 没有第三次发送。

`time.sleep(4)` 是实际的墙钟时间等待，和 C++ 中未调用 `.sleep()` 的临时时长对象不同。

Python 也仅判断 `actionlib.GoalStatus.SUCCEEDED`，失败只记录日志，仍会继续第二个点。`wait_for_server(rospy.Duration(5.0))` 的布尔返回值被忽略；如果服务器没有连上，后续发送和等待不能保证按预期工作。两个 `wait_for_result()` 都没有任务时限。

## 6. Topic、action、文件与默认常量

两个版本都只通过 actionlib 使用相对 action 名 `move_base`，没有额外的普通 topic 发布/订阅，也没有读取或写入业务文件。无命名空间时，action 交互由以下话题承载：

| 方向（以客户端为准） | 话题 | 消息类型 |
| --- | --- | --- |
| 发送 | `/move_base/goal` | `move_base_msgs/MoveBaseActionGoal` |
| 发送取消（本程序未主动调用取消） | `/move_base/cancel` | `actionlib_msgs/GoalID` |
| 接收 | `/move_base/status` | `actionlib_msgs/GoalStatusArray` |
| 接收 | `/move_base/feedback` | `move_base_msgs/MoveBaseActionFeedback` |
| 接收 | `/move_base/result` | `move_base_msgs/MoveBaseActionResult` |

这些是 actionlib 建立的协议接口，不是本包另行手写的五组业务回调。目标中的 `header.frame_id` 使用 `map`；本包不直接读取 TF，目标解释与坐标变换由导航服务端负责。

两份源码都没有 `getParam` / `param` / `rospy.get_param`。目标坐标、action 名、节点名、服务等待间隔和暂停时长都写在源码里，不能通过一份当前不存在的 YAML 修改。

### 多个 goal 与同名节点要分开理解

- `goal1`、`goal2`、`goal3` 是某个进程内的变量名，与其他脚本里的同名变量没有关联。
- actionlib 为每次发送维护 action goal ID；查看 status/result 时应匹配 `goal_id`，不能把状态数组第一个元素当成本程序当前目标。
- 本包 C++ 和 Python 都默认注册 `simple_navigation_goals`；邻包 `set_nav_point` 的示例也使用这个名字。在同一命名空间同时启动会发生 ROS 节点重名冲突。
- 即使改了节点名，不同程序同时向同一个 `move_base` 发送新目标也可能触发目标抢占。改节点名不会自动建立多任务调度。

## 7. 启动前提和构建入口

需要先准备 ROS 1 环境、编译依赖、ROS master 和可连接的 `move_base` action server。外部导航系统还应具备地图/定位、TF、里程计、传感器、规划器和底盘控制链路；本包没有启动这些组件的 launch。

运行前要确认源码中的固定点确实落在当前地图可达区域。`map` 的原点由地图和定位约定决定，这些数字不代表任意场地都能使用。

在成功编译并加载相应 devel 环境后，**已声明的 C++ 目标**对应入口为：

```bash
rosrun multipoint_navigation multipoint_navigation
```

这条命令会立即开始发送固定导航目标，本文没有执行。不要把目录名 `fixed_point_navigation` 当作该命令的包名。

Python 脚本没有安装入口。若后续单独使用，应先检查解释器、依赖和脚本内容，再按源码文件运行方式配置；本文不把它列为现成的 `rosrun` 程序。当前也没有可直接调用的本包 `roslaunch` 文件。

## 8. 代码可证的问题与调试建议

| 检查项 | 已能从代码确认的事实 | 建议 |
| --- | --- | --- |
| 包名混淆 | 目录名、清单 description 与真实包名不一致 | 用 `rospack find multipoint_navigation` 核实实际解析位置 |
| 第三个目标未实现 | `goal3` 未使用，重复发送 `goal2` | 对照源码和 action goal 内容确认实际三次请求 |
| 停留时间无效 | C++ 的 `ros::Duration(7)` 未 sleep | 不要根据注释期待有 7 秒停留 |
| 服务未连接仍继续 | Python 等待 5 秒后未检查结果 | 核实 action server 后再做后续调试 |
| 任务可能一直等待 | `waitForResult()` / `wait_for_result()` 无时限 | 观察 status、规划日志与 TF；后续改进需定义超时和取消策略 |
| 失败仍继续下一点 | 所有结果分支都只是日志 | 明确测试目标失败后是否允许进入下一阶段 |
| 节点重名及目标竞争 | 示例共用 `simple_navigation_goals` 和 `move_base` | 同一导航实例一次只由一个任务程序调度 |
| 安装空间不完整 | C++ 和 Python 都没有安装规则 | 区分源码/devel 环境和仅 install 环境 |

可先进行以下只读检查，本文未执行：

```bash
rospack find multipoint_navigation
rosnode list
rostopic list | grep '^/move_base/'
rostopic info /move_base/goal
rostopic echo /move_base/status
rosrun tf tf_echo map base_link
```

调试时先在仿真或独立测试的 action server 上记录每次请求的目标点、`goal_id` 和终态，确认“失败也继续”和重复目标的行为。若仅 remap action 名到测试服务，需要把整个 action 命名空间一致重映射，不能只改 `/move_base/goal` 而保留其余协议话题。
