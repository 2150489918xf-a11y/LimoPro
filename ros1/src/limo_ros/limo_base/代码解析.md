# limo_base：ROS 1 底盘驱动代码解析

> 分析日期：2026-11-24。本文基于当前仓库的静态源码分析，记录时仓库 HEAD 为 `f6218a8`。已阅读本包的构建文件、全部 C++ 源码与头文件、消息、launch 和两个 Python 示例；未编译、未启动车端程序、未实车测试。下文区分源码已确定的行为、运行前提和待验证项。

## 1. 这个包负责什么

`limo_base` 把 ROS 1 的速度指令转换成底盘串口协议，同时把底盘反馈转换成里程计、IMU 和状态消息。它属于连接上层导航与底盘控制器的驱动层。

```text
上层遥控或导航节点
    └─ /cmd_vel：geometry_msgs/Twist
         └─ twistCmdCallback → setMotionCommand → sendFrame
              └─ Linux 串口 → 底盘控制器

底盘控制器 → 串口字节流
    └─ readData → processRxData → parseFrame
         ├─ 运动反馈 → publishOdometry → /odom、可选的 odom→base_link TF
         ├─ 系统反馈 → publishLimoState → /limo_status
         └─ IMU 反馈 → publishIMUData → /imu，并更新里程计使用的航向
```

本包没有地图、定位、路径规划、激光雷达驱动或传感器安装 TF，也没有软件层的导航任务管理。与它组合使用的启动配置见相邻包的[代码解析](../limo_bringup/代码解析.md)。

## 3. 构建产物、依赖与安装现状

[CMakeLists.txt](CMakeLists.txt) 的实际行为如下：

1. 查找 catkin 组件 `roscpp`、`geometry_msgs`、`tf`、`message_generation`。
2. 注册 `LimoStatus.msg`，以 `std_msgs` 为消息依赖生成代码。消息中的 `Header` 对应 `std_msgs/Header`。
3. 编译 `limo_base_node.cpp`、`limo_driver.cpp`、`serial_port.cpp`，生成一个可执行程序 **`limo_base_node`**；没有单独导出的底盘驱动库。
4. 显式设置节点依赖 `limo_base_generate_messages_cpp`，保证使用本包消息头文件前先生成消息。
5. 显式安装节点到 catkin 包二进制目录、`launch/` 到包共享目录。

需要区分“能在已有工作区运行”与“包的构建声明完整”：

| 项目 | 源码中的现状及影响 |
| --- | --- |
| 依赖声明 | `package.xml` 只声明 catkin、`roscpp`、`geometry_msgs`、`tf`，未声明 `message_generation`、`message_runtime`、`std_msgs`、`nav_msgs`、`sensor_msgs`；后两者直接出现在驱动头文件中 |
| catkin 查找 | `find_package(catkin COMPONENTS ...)` 未显式列出 `std_msgs`、`nav_msgs`、`sensor_msgs`；现有环境可能通过其他包获得部分传递依赖，干净环境需要检查 |
| 包导出 | 没有 `catkin_package(...)`，未显式导出依赖、头文件或消息运行时关系 |
| Python 示例 | 没有 `catkin_install_python(...)` 或脚本安装规则，且 `pylimo` 不在清单中 |
| 头文件 | 没有 `include/` 的显式安装规则；不能按已发布的 C++ 库使用本包 |

消息生成宏可能另有自动生成或安装行为，因此这里不把“没有手写 msg 安装规则”等同于“消息一定不会安装”。但当前文件不足以证明本包可在干净环境完成独立构建、安装及下游引用，需实际验证。

## 4. 节点如何启动

### 4.1 主线程与读取线程

入口见 [main()](src/limo_base_node.cpp#L33)：`ros::init(..., "limo_node")`，构造 `AgileX::LimoDriver` 后调用 `ros::spin()`。

通过 [limo_base.launch](launch/limo_base.launch) 启动时，节点名被设置为 **`limo_base_node`**；直接 `rosrun limo_base limo_base_node` 时，未额外重命名则使用代码中的 **`limo_node`**。查询私有参数时要对应实际节点名。

[构造函数](src/limo_driver.cpp#L36) 依次：

1. 使用私有句柄 `~` 读取参数。
2. 若 `use_mcnamu=true`，先把软件运动模式设为麦克纳姆模式。
3. 建立三个发布者和 `/cmd_vel` 订阅者。
4. 若串口名包含 `tty`，前面拼接 `/dev/`，按 `B460800` 打开。
5. `connect()` 成功后创建 `readData()` 线程。
6. 发送一次 `enableCommandedMode()` 控制模式配置帧。

主线程通过 `ros::spin()` 处理速度回调，接收线程读取并解析底盘数据。这两个线程会访问共同的运动模式变量，详见后面的待验证问题。

### 4.2 参数与默认值

| 私有参数 | C++ 默认值 | 本包 launch 默认值 | 实际作用 |
| --- | --- | --- | --- |
| `~port_name` | `ttyTHS1` | `ttyTHS0` | 串口设备的短名称，驱动自行添加 `/dev/` |
| `~odom_frame` | `odom` | `odom` | `/odom.header.frame_id`，也用作可选 TF 的父坐标系 |
| `~base_frame` | `base_link` | `base_link` | `/odom.child_frame_id`，也用作可选 TF 的子坐标系 |
| `~use_mcnamu` | `false` | `false` | 强制驱动按麦克纳姆运动模式解释、发送数据；保留源码中的拼写 |
| `~pub_odom_tf` | `false` | `false` | 是否发送 `odom_frame → base_frame`；不影响 `/odom` 消息发布 |

参数仅在构造时读取。源码没有动态参数回调，运行时修改参数服务器并不意味着驱动会应用新值。

串口名存在特殊限制：应传 `ttyTHS0`、`ttyUSB0` 等短名称。传 `/dev/ttyUSB0` 会被拼成 `/dev//dev/ttyUSB0`；不含 `tty` 的自定义别名则根本不会进入连接分支。波特率在驱动中固定为 460800，当前没有 launch 参数可以修改。

`use_mcnamu` 是驱动软件中的模式选择，不会改变车轮机构。`enableCommandedMode()` 发送的是控制模式配置，也不能据此认定它会把底盘切换为差速或阿克曼模式。

## 5. ROS 输入、输出和 TF

以下话题都在 C++ 中写成绝对名称，普通命名空间不会自动改变它们；需要 ROS remap 才能改名。

| 方向 | 名称 | 类型 | 触发与内容 |
| --- | --- | --- | --- |
| 输入 | `/cmd_vel` | `geometry_msgs/Twist` | 队列 5；按当前模式使用 `linear.x`、`linear.y`、`angular.z` |
| 输出 | `/odom` | `nav_msgs/Odometry` | 队列 50，latched；收到 `0x221` 运动反馈时计算并发布 |
| 输出 | `/imu` | `sensor_msgs/Imu` | 队列 10，latched；收到 `0x323` 欧拉角反馈时发布缓存的 IMU 数据 |
| 输出 | `/limo_status` | `limo_base/LimoStatus` | 队列 10，latched；收到 `0x211` 系统状态时发布 |
| 可选输出 | `/tf` | TF 变换 | 仅 `pub_odom_tf=true` 时发送 `odom_frame → base_frame` |

`latched` 表示新订阅者可立即收到上一条消息，不等于数据仍在更新。判断链路是否正常应同时检查时间戳和频率。

`LimoStatus` 包含 `header`、`vehicle_state`、`control_mode`、`battery_voltage`、`error_code`、`motion_mode`。本包只明确给出运动模式枚举：`0x00` 四轮差速、`0x01` 阿克曼、`0x02` 麦克纳姆。其他状态数值的业务含义需要结合底盘协议资料，不能从字段名猜测。

驱动的 IMU 消息坐标系固定为 **`imu_link`**，不受 `base_frame` 参数影响。本包不发布 `base_link → imu_link`、雷达或相机安装 TF；这些在 `limo_bringup/limo_start.launch` 中配置。独立启动本包时需要另行提供所需传感器变换。

## 6. 串口与协议：真正发送和接收了什么

### 6.1 串口设置

[SerialPort::openPort()](src/serial_port.cpp#L36) 使用 Linux `open`、`fcntl` 和 `termios`：原始模式、8 数据位、无校验、1 停止位；`VMIN=1`、`VTIME=0`，并通过 `fcntl(..., 0)` 恢复阻塞读取。驱动指定 460800 波特率。

[readData()](src/limo_driver.cpp#L95) 每次调用 `readByte()` 读取一个字节，交给状态机。`writeData()` 直接调用一次系统 `write()`，上层未检查返回值或补写短写数据。

### 6.2 固定 14 字节帧

结合 [limo_protocol.h](include/limo_protocol.h#L38)、[processRxData()](src/limo_driver.cpp#L105) 与 [sendFrame()](src/limo_driver.cpp#L322)，本实现使用：

| 字节偏移 | 长度 | 内容 |
| --- | --- | --- |
| `0` | 1 | 帧头 `0x55` |
| `1` | 1 | 帧长 `0x0E`，即 14 字节 |
| `2..3` | 2 | 消息 ID，高字节在前 |
| `4..11` | 8 | 消息数据 |
| `12` | 1 | 计数字段；接收时保存为 `frame.count`，发送数组初始化后保持为 0 |
| `13` | 1 | 八个数据字节之和的低 8 位 |

校验和没有把帧头、长度、消息 ID 和计数字节加进去，也不是 CRC。`sendFrame()` 没有使用传入结构中的 `count` 或维护递增序号。

接收状态顺序为：帧头 → 长度 → ID 高字节 → ID 低字节 → 八个数据字节 → count → 校验。校验通过后调用 `parseFrame()`；校验失败会打印错误并清理本帧状态。`frame.stamp` 在识别帧头时使用 ROS 当前时间记录，不是控制器内部硬件时间戳。

### 6.3 已实现的消息

| ID | 方向与处理 | 数据解释 |
| --- | --- | --- |
| `0x421` | 发送：`enableCommandedMode()` | 第一个数据字节 `0x01`，其余为 0；构造时发送一次 |
| `0x111` | 发送：`setMotionCommand()` | 四组有符号 16 位大端值，顺序为前向速度、角速度、横向速度、转角；各浮点值乘 1000 后编码 |
| `0x221` | 接收：运动状态 | 四组有符号 16 位大端值，各除 1000；转角按正负再乘 `2.47` 或 `1.64`，随后计算里程计 |
| `0x211` | 接收：系统状态 | 数据 0/1 为车辆状态与控制模式；2/3 为电压，乘 `0.1`；4/5 为错误码；6 为运动模式 |
| `0x311` | 接收：轮里程 | 解出左右轮两个 32 位数，但没有参与积分、保存或发布 |
| `0x321` | 接收：IMU 加速度 | 三个有符号 16 位数除 100，缓存到 `imu_data_` |
| `0x322` | 接收：IMU 角速度 | 三个有符号 16 位数除 100，再由度/秒换成弧度/秒，缓存 |
| `0x323` | 接收：IMU 欧拉角 | 按 yaw、pitch、roll 解码并除 100，调用 IMU 发布函数 |
| `0x251..0x254`、`0x261..0x264` | 接收分支存在但为空 | 当前不生成电机级 ROS 状态 |

`0x321` 的实现只做 `/100`，没有乘重力加速度常数。其数值能否直接符合 `sensor_msgs/Imu` 的 m/s² 约定，必须对照控制器协议及静止测量验证，本文不推定原始单位。

[processErrorCode()](src/limo_driver.cpp#L260) 将 `0x0001/0x0002` 记录为电池告警，`0x0004` 为遥控断连，`0x0008/0x0010/0x0020/0x0040` 为四个电机驱动错误，`0x0100` 为驱动状态错误。这里的处理是日志输出，没有因此主动发送停车帧。

## 7. 速度命令如何按模式转换

主入口是 [twistCmdCallback()](src/limo_driver.cpp#L338)。

| 模式 | 输入使用方式 | 发送给 `setMotionCommand` 的顺序 |
| --- | --- | --- |
| 四轮差速 | 使用 `linear.x` 和 `angular.z`，忽略横向速度 | `(vx, wz, 0, 0)` |
| 麦克纳姆 | 使用前向、横向与旋转三个分量 | `(vx, wz, vy, 0)` |
| 阿克曼 | 从 `vx / wz` 求转弯半径，再求中心转角与内轮转角 | `(vx, 0, 0, steering_angle)` |

默认 `use_mcnamu=false` 时，当前运动模式在收到 `0x211` 系统反馈后写入；不是由某个名为“差速导航”的 launch 自动设定。`use_mcnamu=true` 时，后续系统反馈不会覆盖软件模式。

阿克曼转换使用头文件中的硬编码常量：轮距 `0.172 m`、轴距 `0.2 m`，并使用 `convertCentralAngleToInner()` 与 `convertInnerAngleToCentral()`。这些值没有 ROS 参数入口。

阅读 `setMotionCommand()` 时以 `.cpp` 定义为准：实际参数顺序是 **前向速度、角速度、横向速度、转角**。[头文件声明](include/limo_driver.h#L59) 的部分形参名称与实现含义不一致；因为四个参数都是 `double`，这不会产生类型层面的编译错误，却容易误导调用者。

## 8. IMU 与里程计：位姿是怎样算出来的

### 8.1 IMU 消息与航向缓存

[publishIMUData()](src/limo_driver.cpp#L384) 将先前缓存的加速度、角速度填入消息。虽然欧拉角帧解出了 roll、pitch、yaw，发布的四元数只使用 `setRPY(0, 0, yaw)`，相当于平面航向。

另有一套供里程计使用的航向累计，单位是度：

```text
第一帧：last_theta = 当前 yaw，real_theta 初始为 0
每一帧：delta_theta = 当前 yaw - 上一帧 yaw
        若 -0.1 < delta_theta < 0.1，则把本次增量置 0
        real_theta += delta_theta
        last_theta = 当前 yaw
```

因此 `/imu.orientation` 使用反馈的 yaw，而 `/odom` 航向使用从首次 IMU 帧开始累计的 `real_theta`。初始 IMU yaw 不为 0 时，两者不一定具有相同零点。

### 8.2 速度与位置积分

[publishOdometry()](src/limo_driver.cpp#L435) 在每一帧 `0x221` 到来时执行。第一帧 `dt=0`，此后 `dt` 为相邻运动反馈帧头接收时间之差。

先按模式算车体速度：

- 差速：`vx=linear_velocity`，`vy=0`，`wz=angular_velocity`。
- 麦克纳姆：直接使用反馈的前向、横向、角速度。
- 阿克曼：用转角和几何常量求半径与中心转角，再求 `wz`、`vx`、`vy`；其中倒车时 `vy` 使用 `linear_velocity * sin(-central_angle)`，应结合坐标约定验证。

然后用 **IMU 累计航向** 将车体速度转到里程计平面：

```text
heading = degToRad(real_theta)
x += (cos(heading) * vx - sin(heading) * vy) * dt
y += (sin(heading) * vx + cos(heading) * vy) * dt
odom_orientation = QuaternionFromYaw(heading)
```

需要特别理解：

- 当前实现没有用 `theta += wz * dt` 更新朝向，`wz` 只是填入 `/odom.twist.twist.angular.z`。
- 当前实现没有用 `0x311` 的轮累计里程计算位置。
- 如果 IMU 航向不更新，里程计朝向也不会靠角速度自动积分补上。
- 位置积分使用帧头时间，但 `/odom` 及其 TF 时间戳使用发布时的 `ros::Time::now()`。
- `/odom.pose.covariance` 使用固定对角值；`twist.covariance` 没有显式填写。IMU 三组协方差也使用固定值，未显示测量标定依据。
- 加速度、角速度和欧拉角由不同帧缓存，没有时间同步或“数据是否已齐全”的检查。

## 9. 源码可确认的问题与验证建议

以下是当前实现可以定位的事实及其风险，不代表已观察到对应实车故障；本次没有修改这些实现。

| 问题 | 源码证据与可能影响 | 建议如何验证 |
| --- | --- | --- |
| 阿克曼零指令未做分支处理 | [速度回调](src/limo_driver.cpp#L345) 直接执行 `vx/wz`。`vx=0,wz=0` 时可能产生 NaN，后续转角换算及整数编码没有有限值检查 | 在独立测试环境构造零指令、直行、正反转弯组合，检查编码结果是否都是有限且符合协议的数值 |
| 转角限幅单位不一致 | [常量](include/limo_driver.h#L102) 将 `28.0` 注释为 degree；[回调](src/limo_driver.cpp#L353) 将 `atan` 得到的弧度直接与它比较，未换成约 `0.4887 rad` | 检查期望最大内轮角与输出协议转角的单位，覆盖极小半径输入；不要把该比较当作已实现 28° 限幅 |
| 左右转向缩放不对称 | [回调](src/limo_driver.cpp#L363) 正负分支都除 `right_angle_scale_`；[反馈解析](src/limo_driver.cpp#L176) 则正值乘 `left_angle_scale_`、非正值乘 `right_angle_scale_` | 对照底盘标定与协议，检查同幅左右转向的指令/反馈是否相互对应；不能仅凭变量名决定应替换哪个值 |
| 模式与 IMU 缓存未完整初始化 | [类成员](include/limo_driver.h#L99) 的 `motion_mode_`、`imu_data_` 没有初始化；模式仅在强制麦轮或系统帧到来后赋值 | 检查首帧顺序；分别模拟先到运动帧、先到欧拉角帧，以及系统状态尚未来时收到命令 |
| 两线程共享模式没有同步 | 接收线程在 [系统状态分支](src/limo_driver.cpp#L192) 写 `motion_mode_`，ROS 回调线程读取；当前无 mutex/atomic | 在隔离的 C++ 测试构建中使用线程检测，审查启动和切换模式时的访问 |
| 没有主机侧命令超时停车 | 发送只发生在命令回调，析构函数为空；没有定时器、超时归零或退出停车 | 查控制器是否另有看门狗，再设计断开命令源的受控验证；不能假设停止 ROS 发布就会停车 |
| 命令没有范围、NaN 或 Inf 检查 | [setMotionCommand](src/limo_driver.cpp#L302) 直接将 `double*1000` 转成 `int16_t` | 离线覆盖超范围与非有限输入，确认不会产生不可解释的协议数据 |
| 串口路径与异常处理有限 | [构造函数](src/limo_driver.cpp#L56) 无条件拼 `/dev/`；写入未处理短写/错误，读取错误后只继续循环 | 在伪终端或隔离串口测试中覆盖完整路径、非 tty 别名、断连与短写；不占用真实控制串口做盲测 |
| 线程退出管理不完整 | [析构函数](src/limo_driver.cpp#L64) 没有 join/detach；读取又可能阻塞。`std::thread` 在仍 joinable 时析构会触发终止 | 检查 Ctrl+C、无串口数据时退出及串口断开路径，设计可停止的读取与线程回收 |
| 航向阈值与跨界处理需检查 | [IMU 航向累计](src/limo_driver.cpp#L401) 丢弃每次小于 `0.1°` 的增量，并且始终更新上一帧值；没有处理 ±180°/360° 跨界 | 用缓慢转向和跨界样本检查累计值。跨界可产生约 360° 的累计数值变化，但四元数可能仍等价，不能据此断言 TF 必然跳变 |
| 依赖和导出声明不完整 | 见第 3 节的清单与 CMake 对照 | 在独立 Linux 工作区验证依赖解析、构建、安装和消息下游引用，避免旧 `devel/` 掩盖缺项 |

## 10. 有条件的构建、启动与检查示例

以下命令仅供之后在 Linux 的 **ROS 1 Noetic** 环境人工执行；本文编写过程中没有运行。不要在 Windows PowerShell 或已加载 ROS 2 的终端直接使用。

### 10.1 构建与环境

前提：已准备 catkin 工作区，将源码放入其 `src/`，并核对第 3 节的消息、依赖和导出问题。建议在独立工作区验证，保留已有可运行环境。

```bash
# 将下面路径替换为实际 catkin 工作区根目录。
LIMO_ROS1_WS="/绝对路径/你的ROS1工作区"
source /opt/ros/noetic/setup.bash
cd "$LIMO_ROS1_WS"
catkin_make
source devel/setup.bash
rospack find limo_base
rosmsg show limo_base/LimoStatus
```

`catkin_make` 是构建示例，不表示当前包已通过验证。如果完整仓库中其他包缺依赖，整个工作区也可能构建失败。安装空间的检验应另行执行，不能用 devel 空间可运行代替。

### 10.2 单独启动底盘

前提：确认设备实际对应 `/dev/ttyTHS0`、账户有串口权限、没有其他程序占用同一串口，且当前没有其他节点发布 `odom → base_link`。该启动会发送使能控制帧，应具备现场停止手段。

```bash
# 仅在上述前提满足时执行。串口参数传短名称。
roslaunch limo_base limo_base.launch port_name:=ttyTHS0 pub_odom_tf:=true
```

如果上层使用 `robot_pose_ekf` 等节点负责同一条里程计 TF，应让驱动保持 `pub_odom_tf:=false`，避免同一变换多源发布。启动不同名节点仍可能争用同一个串口，不能用“节点名不同”判断可同时运行。

### 10.3 在已经启动的系统中观察

前提：已 source 对应 ROS 1 工作区，且 ROS Master 和驱动在运行。

```bash
rosnode info /limo_base_node
rostopic info /cmd_vel
rostopic hz /odom
rostopic hz /imu
rostopic echo -n 1 /limo_status
rostopic echo -n 1 /odom/header
rostopic echo -n 1 /imu/header

# 仅在已安排某个节点发布此 TF 时检查。
rosrun tf tf_echo odom base_link
```

本节故意不提供自动发送非零速度的命令。后续运动验证应先明确模式、转角问题和停止条件，再验证直行、旋转、横移或阿克曼转弯。

### 10.4 两个 Python 示例的使用边界

`limomove.py` 实例化外部 `pylimo.LIMO`、使能控制，并循环发送 10 次 `linear_x=0.1, angular_z=-0.01`，每次间隔 `0.3 s`；末尾没有显式零速度命令。它不通过 ROS `/cmd_vel`。

`limogetmessage.py` 同样使用 SDK，每 `0.1 s` 打印一次前向速度。两者都没有由本包 launch 启动，也没有被 CMake 安装。由于 SDK 的设备选择与串口实现不在本包中，执行前还需核查 SDK 版本和串口占用；不能与底盘节点默认并行操作同一个控制串口。

## 11. 初学者应完成的阅读检查

读完后，应能沿源码回答：一条 `/cmd_vel` 如何变成 14 字节帧；`0x221`、`0x323` 各在什么时候改变里程计；为什么没有 IMU 更新时朝向不会自动由 `wz` 补算；什么时候需要打开驱动 TF、什么时候应交给 EKF；为什么当前包的构建声明还不能代表完整可复现环境。

进入建图导航前，再阅读 [limo_bringup 包解析](../limo_bringup/代码解析.md)，确认所选 launch 真正启动的节点和需要额外提供的输入。
