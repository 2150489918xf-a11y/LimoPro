# limo_bringup：ROS 1 建图与导航启动配置解析

> 分析日期：2026-11-24。本文基于当前仓库的静态源码分析，记录时仓库 HEAD 为 `f6218a8`。已阅读 `package.xml`、`CMakeLists.txt`、全部 16 个 launch、`param/` 中的 YAML/Lua、地图描述文件、RViz 相关配置及三个 Python 脚本；未编译、未启动车端程序、未实车测试。外部 ROS 包的行为需结合实际安装版本核对，本文不把配置文件存在视为运行成功。

## 1. 这个包在系统中的职责

`limo_bringup` 主要用 launch 组织外部 ROS 节点，用参数文件配置定位、代价地图和规划器。底盘驱动实现在相邻的 `limo_base` 中，Gmapping、Cartographer、AMCL、move_base、RTAB-Map 算法实现在各自的外部包中。

学习本包时，最重要的是先区分三件事：

1. launch 中实际声明了哪些节点或 include。
2. 启动的节点需要哪些已经存在的话题和 TF。
3. 某个参数文件究竟有没有被这个入口加载、加载到了哪个命名空间。

例如，`limo_navigation_rtabmap.launch` 当前只启动 `move_base`；`limo_rtabmap_realsense.launch` 当前不启动 RealSense 相机驱动。仅凭文件名不能判断系统已经具备地图、定位或相机数据。

## 3. 构建与安装：它为什么没有可编译的导航源码

[CMakeLists.txt](CMakeLists.txt) 只有 `cmake_minimum_required`、`project(limo_bringup)`、`find_package(catkin REQUIRED)`。因此：

- 没有 `add_executable`、`add_library` 或消息生成，不会编译出本包自己的导航算法节点。
- 没有 `catkin_package()`，包导出声明不完整。
- 没有安装 `launch/`、`param/`、`maps/`、`rviz/`、`scripts/` 的规则，也没有 `catkin_install_python()`。
- `package.xml` 只声明 `catkin` 构建工具，没有声明 launch 所需的运行依赖。

在 source/devel 工作区内，`rospack` 可能直接找到源码目录，因而 `$(find limo_bringup)/launch/...` 能被解析；这不能证明仅使用 install 空间时仍能找到这些资源。后续若需要标准化部署，应补充构建导出、运行依赖与资源安装规则，再在干净工作区验收。本次仅记录现状。

## 5. 基础启动与 TF：先让数据坐标系连起来

### 5.1 limo_start.launch 的实际作用

[limo_start.launch](launch/limo_start.launch) 提供 `port_name=ttyTHS0`、`use_mcnamu=false`、`pub_odom_tf=false`，向底盘 launch 传递这三个参数；没有转发 `odom_frame`、`base_frame` 参数。

外部雷达入口写死为 `$(find ydlidar_ros_driver)/launch/Tmini.launch`。该驱动不在本仓库当前的 ROS 1 源码包中，其内部节点名、串口、扫描帧和默认参数必须检查实际安装文件。

另外定义以下安装变换，位置单位为米，旋转参数全部为 0：

| 节点名 | 父 → 子，按源码写法 | 平移 `(x, y, z)` |
| --- | --- | --- |
| `base_link_to_camera_link` | `/base_link → /camera_link` | `(0.105, 0, 0.1)` |
| `base_link_to_imu_link` | `/base_link → /imu_link` | `(0, 0, 0)` |
| `base_link_to_laser_link` | `/base_link → /laser_link` | `(0.105, 0, 0.08)` |

这里使用旧版 **`tf/static_transform_publisher`**，最后一个参数 `10` 表示发布周期 10 ms；不要按 `tf2_ros` 的一次性 `/tf_static` 发布方式解释。实际传感器的 `header.frame_id` 必须能连到这些坐标系，安装偏移也需要核对实物。

建立 `camera_link` 只是建立一个坐标系，不会产生图像、深度数据或相机 optical frame。相机驱动若也发布相同安装 TF，需要确认由谁负责。

### 5.2 差速/阿克曼 AMCL 导航的预期链路

```text
map ──AMCL──> odom ──robot_pose_ekf──> base_link
                                      ├─安装TF─> laser_link
                                      ├─安装TF─> imu_link
                                      └─安装TF─> camera_link
```

这是这些配置的组合意图，需要运行时验证。导航 launch 为 EKF 设置 `output_frame=odom`、`base_footprint_frame=base_link`，并把 `imu_data` remap 到 `imu`。底盘发布 `/odom`、`/imu`，其默认 `pub_odom_tf=false` 可以为 EKF 留出里程计 TF 的发布权。

若同时打开驱动的 `pub_odom_tf=true`，又由 EKF 发布 `odom → base_link`，会出现同一变换多源问题。因此不能把“打开 TF”作为所有 launch 的统一修复办法。

同样，不要同时启动多个建图/定位入口：它们可能争用 `map` 相关 TF、`/map` 和相同节点名。Cartographer 的当前 Lua 还有另一种 TF 输出配置，见下一节。

## 6. 建图、定位与导航启动链

### 6.1 Gmapping：EKF + 激光建图

[limo_gmapping.launch](launch/limo_gmapping.launch) 创建 EKF、`slam_gmapping`、RViz；没有 include `limo_start.launch`。

内联参数包括地图分辨率 `delta=0.05`、`maxUrange=16.0`、`particles=30`、地图更新间隔 `5.0 s`，运动更新阈值为 `linearUpdate=1.0`、`angularUpdate=0.5`。这些是当前参数值，不是针对所有场地的推荐值。

输入需要已有扫描数据及匹配的传感器/里程计 TF。这里没有给 Gmapping 另设话题 remap，话题默认值依赖外部实现；通常应检查其实际 `/scan` 订阅和 `map → odom` 发布。

本入口的 `<remap from="imu_data" to="imu"/>` **被注释掉了**，与差速、阿克曼和独立 AMCL 入口不同。底盘实际发布 `/imu`，不能仅因为启动了 EKF 就认定它已经融合 IMU；需检查安装版 EKF 的订阅话题与参数。

### 6.2 Cartographer：二维建图与状态加载

[limo_cartographer.launch](launch/limo_cartographer.launch) 设置 `/use_sim_time=false`，给 `cartographer_node` 传入 [build_map_2d.lua](param/build_map_2d.lua)，启动分辨率 `0.05` 的 occupancy grid 节点和 RViz。XML 中还有字面上的 `horizontal_laser_2d → scan` remap，其是否对应安装版 Cartographer 的实际输入名称，需要检查节点订阅。

Lua 中明确设置：

- `map_frame="map"`、`tracking_frame="base_link"`、`published_frame="base_link"`、`odom_frame="odom"`。
- `use_odometry=true`，`TRAJECTORY_BUILDER_2D.use_imu_data=true`：里程计与 IMU 都是本配置要求的数据源。
- 一路单线激光扫描，`min_range=0.3`、`max_range=8.0`，使用二维轨迹构建。
- `provide_odom_frame=false`。在启用正常 TF 发布的 Cartographer 配置语义下，这对应直接向 `published_frame` 发布，即 **`map → base_link`**，不能把它画成已经配置好的 `map → odom → base_link`。

因此这一配置与 AMCL/EKF 路线不能机械拼接。若下游导航要求 `map → odom → base_link`，应先确定 TF 分工和 Cartographer 版本行为，再审查 `published_frame`、`provide_odom_frame` 等配置；本次未修改参数。

[limo_cartographer_local.launch](launch/limo_cartographer_local.launch) 使用 [location.lua](param/location.lua)，并从硬编码路径 `/home/agilex/agilex_ws/src/limo_ros/limo_bringup/maps/map.pbstream` 加载状态。这个入口：

- 只启动 Cartographer 和 RViz，occupancy grid 节点整段被注释，不会因为文件里出现其名字就启动它。
- 不启动 map_server、move_base、底盘或雷达。
- Lua 启用 `pure_localization_trimmer={max_submaps_to_keep=3}`。
- `POSE_GRAPH.optimize_every_n_nodes` 先赋值 20、后又赋值 35，按 Lua 顺序最终为 **35**。

`.pbstream` 是 Cartographer 状态，不等同于供 map_server 加载的 YAML/PGM。加载状态不代表当前入口已经提供可供导航使用的 `/map`。

### 6.3 独立 AMCL：只定位，不包含地图服务器和规划器

[limo_amcl.launch](launch/limo_amcl.launch) 启动 EKF、AMCL 和 RViz，加载 [amcl_params_omni.yaml](param/amcl_params_omni.yaml)，使用 `odom_model_type="omni"`，并把初始位置与方向设为 0。

它需要已有地图提供者和传感器数据；不会启动 map_server 或 move_base。它也不会因为使用 omni 模型就把底盘或车轮切到麦克纳姆模式。

### 6.4 差速导航：AMCL + map_server + TrajectoryPlannerROS

[limo_navigation_diff.launch](launch/limo_navigation_diff.launch) 的加载关系是：

```text
robot_pose_ekf：output_frame=odom，base_footprint_frame=base_link，imu_data→imu
amcl：param/amcl_params_diff.yaml，初始 x/y/yaw=0
map_server：maps/map1017.yaml，frame_id=map
move_base：param/diff/{costmap_common,local_costmap,global_costmap,planner}.yaml
rviz：rviz/navigation_diff.rviz
```

move_base 明确选择 `global_planner/GlobalPlanner` 和 **`base_local_planner/TrajectoryPlannerROS`**，规划频率 `1 Hz`、控制频率 `5 Hz`，允许恢复时旋转。

[planner.yaml](param/diff/planner.yaml) 同时保存 `NavfnROS`、`TrajectoryPlannerROS`、`DWAPlannerROS` 三组配置。当前入口没有选择 Navfn 或 DWA 插件，因此修改这两组不等于修改正在使用的规划器。

当前 TrajectoryPlannerROS 的 `max_vel_x=0.6`、`max_vel_theta=1.0`、`holonomic_robot=false`、`dwa=false`、`xy_goal_tolerance=0.2`、`yaw_goal_tolerance=0.15`。这里是 TrajectoryPlannerROS 的轨迹采样配置，不能只因文件里有 DWA 段就把本入口称为 DWA 导航。

代价地图使用 `map` 作为 global/local 的全局参考系，底座为 `base_link`；局部窗口 `4.5 m × 4.5 m`、分辨率 `0.05 m`。输入障碍源配置为 `LaserScan` 的 `scan`，最终解析话题名需结合运行命名空间核对。

### 6.5 阿克曼导航：使用的是 carlike2 参数

[limo_navigation_ackerman.launch](launch/limo_navigation_ackerman.launch) 同样启动 EKF、AMCL、map_server、move_base、RViz，但配置不同：

| 项目 | 实际引用 |
| --- | --- |
| AMCL | [param/amcl_params.yaml](param/amcl_params.yaml)，当前 `odom_model_type="diff"` |
| 地图 | [maps/map11.yaml](maps/map11.yaml) |
| 代价地图与 TEB | **[param/carlike2/](param/carlike2/)**，不是 `param/ackerman/` |
| 全局规划器 | `global_planner/GlobalPlanner` |
| 局部规划器 | `teb_local_planner/TebLocalPlannerROS` |
| 恢复旋转 | `clearing_rotation_allowed=false` |

[TEB 参数](param/carlike2/teb_local_planner_params.yaml) 使用 `wheelbase=0.2`、`min_turning_radius=0.3`、`max_vel_x=1.0`，并设 `cmd_angle_instead_rotvel=false`。后者表示保持 `Twist.angular.z` 的角速度语义，与当前 `limo_base` 阿克曼回调自行换算转角的接口意图一致。

局部代价地图只有 `0.5 m × 0.5 m`、分辨率 `0.1 m`，插件列表只启用 StaticLayer 与 ObstacleLayer，没有 InflationLayer。公共配置里虽然存在 `inflation_layer` 参数，但不能由此认定局部膨胀层已启用。

本入口没有底盘运动模式切换指令；物理机构、控制器模式、驱动解释和规划器约束需一致。底盘回调还存在零指令、转角单位等问题，先读 [底盘包问题清单](../limo_base/代码解析.md)。

### 6.6 RTAB-Map 建图与导航是分开的入口

三个 RTAB-Map 建图入口的节点都位于 `rtabmap` 命名空间中，但其相机输入和包布局并不相同。

| 项目 | RealSense 入口 | Orbbec 主入口 | Orbbec copy 入口 |
| --- | --- | --- | --- |
| 文件 | [limo_rtabmap_realsense.launch](launch/limo_rtabmap_realsense.launch) | [limo_rtabmap_orbbec.launch](launch/limo_rtabmap_orbbec.launch) | [limo_rtabmap_orbbec (copy).launch](launch/limo_rtabmap_orbbec%20%28copy%29.launch) |
| RTAB-Map 节点包 | `rtabmap_ros` | `rtabmap_slam` | `rtabmap_slam` |
| RGB-D 数据方式 | nodelet 先生成 `rgbd_image`，算法 `subscribe_rgbd=true` | 算法直接订阅 RGB、深度与相机信息，`subscribe_depth=true` | 与 RealSense 入口相近，使用 `rtabmap_ros/rgbd_sync` |
| RGB 输入 | `/camera/rgb/image_converted` | 默认 `/camera/color/image_raw`，可用 `rgb_topic` 改 | `/camera/rgb/image_converted` |
| 深度输入 | `/camera/depth/image_rect` | 默认 `/camera/depth/image_raw`，可用 `depth_topic` 改 | `/camera/depth/image_rect` |
| CameraInfo | `/camera/rgb/image_converted/camera_info` | 默认 `/camera/color/camera_info` | `/camera/rgb/image_converted/camera_info` |
| 里程计 | 显式 `odom → /odom` remap | 默认 `rgbd_odometry=false`，给主节点设置 `odom_frame_id=odom`，依赖 TF | 显式 `odom → /odom` remap |
| 地图输出配置 | `grid_map → /map` | `grid_map → /map` | `grid_map → /map` |
| `database_path` 参数 | 声明了 arg，但没传给节点 | 传入主节点，可指定路径 | 声明了 arg，但没传给节点 |
| `wait_for_transform` 参数 | 声明后未使用 | 传入主节点与可选节点 | 声明后未使用 |

补充说明：

- RealSense/copy 的算法节点还写有 `rgb/image`、`depth/image` remap，但其主输入模式为同步后的 `rgbd_image`。真正送入同步器的话题，应看 `rgbd_sync` 的 remap，不要只看算法节点中的旧相机 remap。
- 三个入口都不启动相机或雷达驱动。RGB 图像、深度图像、CameraInfo 的分辨率、时间同步、注册对齐和 TF 必须匹配；按文件名启动不能保证适配当前相机。
- 主 Orbbec 入口的 `rgbd_odometry=true` 才启动视觉里程计。源码注释要求用于没有真实底盘里程计 TF 的测试；不能与其他 `odom → base_link` 发布者未经设计地并行。
- `rtabmap_viz=true` 才启动专用可视化程序，并引用外部 `rtabmap_demos/launch/config/rgbd_gui.ini`；不是 RViz。
- 主 Orbbec 入口中有关 `turtlebot_bringup`、`turtlebot_navigation` 的 include 全部在注释中，不是当前生效依赖或节点。
- 三个入口默认 `localization=false`，此时 `args` 默认为 **`--delete_db_on_start`**。这可能清除节点实际使用的数据库；只有主 Orbbec 入口确实转发了 `database_path`。不能把另外两个入口上的同名 arg 当作数据库路径已生效。
- `localization=true` 时，`args` 默认不带删除标志，设置 `Mem/IncrementalMemory=false` 和 `Mem/InitWMWithAllNodes=true`。是否能定位还取决于数据库、传感器和 TF。
- RealSense/copy 配置 `Grid/FromDepth=false`、`Reg/Strategy=1`，使用激光生成占据栅格与 ICP 注册；主 Orbbec 入口设置 `Reg/Strategy=0`，配置意图偏向视觉注册，不能把三个入口视为同一配置的简单改名。

规划另选一个入口：

- [limo_navigation_rtabmap.launch](launch/limo_navigation_rtabmap.launch)：只启动 move_base，以 `param/4wd/` 选择 GlobalPlanner + DWAPlannerROS。
- [limo_navigation_rtabmap_ackerman.launch](launch/limo_navigation_rtabmap_ackerman.launch)：只启动 move_base，以 `param/carlike2/` 选择 GlobalPlanner + TEB。

这两个入口都没有 EKF。因此，如果底盘保持 `pub_odom_tf=false`，又没有另外的融合/视觉里程计节点，就不能认为 `odom → base_link` 已存在。地图和 `map` 相关定位 TF 同样要由已启动的 RTAB-Map 等组件提供。

## 7. 参数到底由哪个入口加载

| 参数位置 | 当前引用关系 | 学习与修改时的注意点 |
| --- | --- | --- |
| [amcl_params_diff.yaml](param/amcl_params_diff.yaml) | 差速导航 | `odom_model_type=diff` |
| [amcl_params.yaml](param/amcl_params.yaml) | 阿克曼导航 | 同样为 diff 模型；存在 `in_particles` 拼写问题 |
| [amcl_params_omni.yaml](param/amcl_params_omni.yaml) | 独立 AMCL | omni 模型，不是差速导航实际加载文件 |
| [diff/](param/diff/) | 差速导航 | 加载四个 YAML；当前局部规划器为 TrajectoryPlannerROS |
| [carlike2/](param/carlike2/) | 阿克曼导航、RTAB-Map 阿克曼规划 | 当前启用的 TEB 参数组 |
| [4wd/](param/4wd/) | `limo_move_base`、`limo_navigation_rtabmap` | 加载五个 YAML；`1base_local_planner_params.yaml` 没有被这些入口引用 |
| [build_map_2d.lua](param/build_map_2d.lua) | Cartographer 建图 | 通过节点命令行指定配置文件，不是 rosparam YAML |
| [location.lua](param/location.lua) | Cartographer 状态加载/定位 | 同样通过命令行指定 |
| [ackerman/](param/ackerman/) | 当前包内 launch 未引用 | 不是名为 `limo_navigation_ackerman.launch` 的实际参数组 |
| [carlike/](param/carlike/) | 当前包内 launch 未引用 | TEB 中 `wheelbase=0.65`、`cmd_angle_instead_rotvel=true`，与当前启用组不同；含 `.autosave` 文件，不能当作自动生效配置 |
| [NanoRobot_Pro/](param/NanoRobot_Pro/) | 当前包内 launch 未引用 | 另有 `base_footprint` 等配置，不能直接假定适用当前 TF |
| [rtabmap/](param/rtabmap/) | 当前包内 launch 未引用 | 代价地图底座为 `camera_link`，并不是 RTAB-Map 导航入口实际加载的组 |

“未引用”仅指当前包内这 16 个 launch 的引用关系；不排除其他工作区、外部脚本或人工加载它们。

参数文件的层级同样重要。以差速公共参数为例，launch 在 `move_base` 节点内分别用 `ns="global_costmap"` 和 `ns="local_costmap"` 加载，于是 `inflation_layer/inflation_radius` 位于：

```text
/move_base/global_costmap/inflation_layer/inflation_radius
/move_base/local_costmap/inflation_layer/inflation_radius
```

它们与 `local_costmap/inflation_radius` 不是同一个键。参数服务器上“有一个相同名字的数字”，不足以证明正在使用的插件读取了它。

`param/4wd/` 有一个具体的层级问题：

- [global_costmap_params.yaml](param/4wd/global_costmap_params.yaml) 的 `plugins` 写在顶层，而不是 `global_costmap` 下面。
- [local_costmap_params.yaml](param/4wd/local_costmap_params.yaml) 的 `plugins`、`inflation_radius` 也写在顶层。
- 当前 launch 将它们加载进 move_base 私有命名空间，所以出现的是 `/move_base/plugins`、`/move_base/inflation_radius`，不是预期的 `/move_base/global_costmap/plugins` 和 `/move_base/local_costmap/plugins`；后加载的 global 文件还会覆盖同一个顶层 `plugins`。

这是可由 YAML 层级与 launch 加载方式确定的事实。外部 costmap 是否启用旧式参数兼容、最终生成哪些层，还需看安装版本与运行日志，不能据此断言“所有避障一定失效”。

## 8. 话题、动作与 TF 的边界

本包主要配置外部节点，不自己实现以下 ROS 接口。表中区分源码显式配置和依赖外部节点默认行为的内容。

| 接口 | 在本包中的依据 | 核查要点 |
| --- | --- | --- |
| `/cmd_vel`，`geometry_msgs/Twist` | move_base/键盘节点通常输出，底盘明确订阅；本包未给规划节点做速度 remap | 运行时检查实际发布者，避免导航和遥控同时控制 |
| `/odom`，`nav_msgs/Odometry` | 底盘输出；RealSense/copy 有显式 remap，Cartographer Lua 开启 odometry | 消息与 TF 是两件事，有 `/odom` 不代表存在 `odom → base_link` |
| `/imu`，`sensor_msgs/Imu` | 底盘输出；导航/独立 AMCL 给 EKF 做 remap；Cartographer 开启 IMU | Gmapping 的同名 remap 被注释；检查实际订阅、帧和时间戳 |
| `/scan`，`sensor_msgs/LaserScan` | 多个 RTAB-Map 显式 remap、代价地图配置 scan，RViz 显示 `/scan` | 实际数据由外部雷达驱动提供，核查扫描帧与频率 |
| `/map`，`nav_msgs/OccupancyGrid` | map_server、SLAM 常规输出；RTAB-Map 显式 `grid_map → /map` | 不要同时启动多个当前地图源；Cartographer local 未启动 occupancy grid 节点 |
| `/initialpose` | AMCL/RViz 的常规初始位姿接口，导航 RViz 文件中可见 | 启动文件初始位姿写 0 不代表车辆真实位置为原点 |
| `/move_base_simple/goal` | 差速/阿克曼/`rtab_slam.rviz` 中的 RViz 目标工具 | 目标可能触发运动；只在系统验证后使用 |
| `/move_base` 动作接口 | 外部 move_base 的常规 `move_base_msgs/MoveBaseAction` | 本包没有实现多点任务或巡检调度；RTAB-Map 主入口的动作连接示例被注释 |
| `map`、`odom`、`base_link`、传感器帧 | 各 launch、Lua、AMCL/costmap 参数共同约定 | 明确每条 TF 的唯一发布者，Cartographer 的当前配置要单独审查 |

传感器原始串口由底盘或外部雷达包负责。本包除向底盘传 `port_name`、include 外部雷达 launch 外，没有自己的串口收发实现。

## 9. 地图和可视化资源的使用前提

- 差速导航硬编码 [map1017.yaml](maps/map1017.yaml)，阿克曼导航硬编码 [map11.yaml](maps/map11.yaml)，都未提供 `map_file` 一类 launch arg。直接附加一个未声明参数不会自动替换地图。
- 两个 YAML 的分辨率都是 `0.05 m/pixel`，但原点分别是 `(-3.762025, -6.637529, 0)` 与 `(-50, -50, 0)`。应先确认地图对应现场、原点和初始位姿。
- 普通 map_server 地图由 YAML 描述 PGM 路径、分辨率、原点、占用阈值。`.pbstream` 由 Cartographer 使用，不能直接代替 YAML。
- [mymap.pbstream.yaml](maps/mymap.pbstream.yaml) 的 `image` 写死为车端绝对路径；即使 PGM 在仓库内，新设备也未必能按该路径找到它。
- [rtab_slam.rviz](rviz/rtab_slam.rviz) 包含 `/mobile_base/sensors/bumper_pointcloud` 等显示项和 `base_footprint` 视角目标，不能因为 RViz 中有此项就认为当前系统发布了它。
- [rtabmap.rviz](rviz/rtabmap.rviz) 的目标工具写为 `/move_base_simple/goal_tepm`，与通常的 `/move_base_simple/goal` 不同；当前 `rtabmap_rviz.launch` 加载的是另一个 `rtab_slam.rviz`，这个拼写不会直接影响该入口。人工选择 `rtabmap.rviz` 时应核查。

## 10. Python 演示脚本：当前没有接入导航启动链

这三个脚本没有被任何当前 launch 引用，也没有被 CMake 安装；不能把它们描述为已运行的巡检识别功能。

| 文件与主要函数 | 实际行为 | 运行前提与明确问题 |

## 13. 条件化检查与启动示例

以下仅为以后在 Linux ROS 1 环境中人工操作的示例，本次没有执行任何车端命令。先用静态检查确认资源与依赖，再安排唯一一套传感器、TF 和导航链。

### 13.1 已有 ROS 1 工作区：先确认解析到的包

前提：已准备对应工作区及选定路线的依赖，不能沿用混合 ROS 2 环境的终端。

```bash
LIMO_ROS1_WS="/绝对路径/你的ROS1工作区"
source /opt/ros/noetic/setup.bash
source "$LIMO_ROS1_WS/devel/setup.bash"
rospack find limo_bringup
rospack find limo_base
rospack find ydlidar_ros_driver

# 仅解析节点列表和参数，不启动这些节点；仍要求相关包和资源可被找到。
roslaunch --nodes limo_bringup limo_navigation_diff.launch
roslaunch --dump-params limo_bringup limo_navigation_diff.launch
```

overlay 中可能有同名包。若 `rospack find` 指向旧车端目录，修改仓库副本不会改变实际加载内容。若缺包或消息，先处理构建/依赖；本包本身没有可以独立编译出的导航可执行程序。

### 13.2 选择 AMCL 差速导航时

仅在以下条件满足时采用此组合：串口与雷达已确认、没有重复底盘节点，车辆确为差速模式；`map1017.yaml` 已核对为当前场景地图；依赖、参数问题已审查，允许现场启用底盘控制。

```bash
# 终端 A：基础硬件与安装 TF；保留里程计 TF 给后续 EKF。
roslaunch limo_bringup limo_start.launch port_name:=ttyTHS0 pub_odom_tf:=false

# 终端 B：同样先 source ROS 1 和工作区，且终端 A 数据正常后再启动。
roslaunch limo_bringup limo_navigation_diff.launch
```

阿克曼路线应改选 `limo_navigation_ackerman.launch` 并重新核对模式、TEB、地图和底盘转角问题，不与差速入口同时运行。原文件没有通用地图路径 arg，需要另行设计配置后才能切换地图；本文不替读者假设地图通用。

### 13.3 选择 RTAB-Map 已有数据库定位时

前提：使用主 Orbbec 入口支持的 RTAB-Map 包布局；已有外部相机、雷达话题和完整安装 TF；数据库兼容且路径明确。默认 `rgbd_odometry=false`，因此还必须已经安排一个 `odom → base_link` 发布者。

```bash
# 将数据库路径替换为真实、已验证的已有地图数据库。
roslaunch limo_bringup limo_rtabmap_orbbec.launch \
  localization:=true \
  rgbd_odometry:=false \
  database_path:=/绝对路径/已验证的地图.db
```

该命令只启动此配置中的定位/建图节点，不启动相机或规划器。只有地图、定位 TF、传感器都通过检查，并审查第 7 节的 4wd 参数问题后，才考虑额外启动对应的 move_base 入口。RealSense/copy 入口的同名 `database_path` arg 没有传给节点，不适用上面的路径指定方式。

### 13.4 对已运行系统做只读检查

前提：相应节点已由现场人员启动，检查终端已加载同一个 ROS 1 环境。

```bash
rosnode list
rostopic info /cmd_vel
rostopic hz /scan
rostopic hz /odom
rostopic hz /imu
rostopic echo -n 1 /scan/header
rosrun tf tf_echo base_link laser_link
```
